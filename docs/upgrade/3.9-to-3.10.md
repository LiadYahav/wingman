# Upgrade: 3.9 → 3.10 (Wingman picks the MCE for a new cluster)

For an agent inside the disconnected environment. Follow the steps in order.
Every check says what to do when it fails, and **STOP** means: change
nothing more, finish the report (step 9) and hand it back.

`<ns>`, `<release>`, `<tag>`, `$CHART`, `<mce>`, `<domain>`, `<sa-ns>` and
`<sa>` mean what they mean in [3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is
`3.10.0` or a later 3.10 release.

## 1. What changes

| Area | 3.9 | 3.10 |
|---|---|---|
| Create a cluster | the person chooses the site and the MCE | with live status on (`clusterStatus.enabled`), the person chooses the site, prod or prep, the version and the owner, and Wingman picks the MCE: of those at the site that host the version, have enough free pods on their workers, have enough healthy free servers of each node type the nodepools need, and can be read, the one with the fewest clusters of this owner, then the fewest clusters, then the most usable spare servers. The form shows every candidate's numbers and why; an admin may choose another MCE that passes every check, with a reason, and the merge request records it (ADR-0050) |
| What day1 reads on each MCE hub | the 3.4 reads | also `list` on `nodes` and `pods`, cluster-wide (step 5). Pods are read as short Table rows (name, status, node), never their objects, logs or Secrets |
| The tokens Secret | `<mce>: <token>` | the same, or `<mce>: {token: <token>, url: https://<host>:<port>}` for a hub whose API is not `https://api.<mce>.<domain>:6443` (ADR-0045, step 6, optional) |
| Chart | — | `day1.placementMinFreePods` (`PLACEMENT_MIN_FREE_PODS`, default `70`): the free pods an MCE needs to be offered |
| Metrics | — | `kubernetes` gains `list_nodes` and `list_pods`; a new counter, `wingman_placement_decisions_total{decision}` (`docs/ops/metrics.md`) |

With live status off, nothing changes for creates: the form keeps its MCE
select, and `GET /api/day1/placement` answers 501. Skip steps 4 to 6 and
record it.

**Grant before you upgrade.** With live status on, an MCE whose token may not
list nodes and pods is never picked, so a site and env where no MCE has the
grant cannot create a cluster until step 5 is done. The grant works on 3.9
too.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for 3.9.

## 3. Discover (read-only)

```bash
helm list -n <ns>
helm history <release> -n <ns> | tail -3                   # the revision to roll back to
kubectl -n <ns> get deploy -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image
kubectl -n <ns> get configmap wingman-config -o jsonpath='{.data.CLUSTER_STATUS_ENABLED}{"\n"}'
```

Record the running version. **STOP** if it is not a 3.9 release: upgrade to
3.9 first ([3.8-to-3.9.md](3.8-to-3.9.md)). If live status is `false`, skip to step 7.

List the MCEs that have a token (names only, never the tokens), as in
[3.3-to-3.4.md](3.3-to-3.4.md) step 3; this prints the top-level keys, in
either form of the Secret:

```bash
kubectl -n <ns> get secret mce-sa-tokens -o jsonpath='{.data.tokens}' | base64 -d \
  | sed -n 's/^\([^[:space:]#][^:]*\):.*/\1/p'
```

For each `<mce>`, record `<sa-ns>` and `<sa>` (3.3-to-3.4 step 3 has the
`oc whoami` command). An entry in the mapping form keeps its token on its own
`token:` line; read it with:

```bash
TOKEN=$(kubectl -n <ns> get secret mce-sa-tokens -o jsonpath='{.data.tokens}' | base64 -d \
  | sed -n '/^<mce>:/,/^[^[:space:]]/s/^[[:space:]]*token:[[:space:]]*//p' | tr -d "\"'")
```

Also record, from the day1 repo, which sites have more than one MCE per env
(`sites/<site>/mces/`): those are where Wingman's pick matters.

## 4. Check

1. **You can change the grant on each hub.** Logged in to each hub:

   ```bash
   oc auth can-i update clusterroles.rbac.authorization.k8s.io     # yes
   oc get clusterrole wingman-mce-reader -o yaml                    # the 3.4 grant
   ```

   If you cannot update ClusterRoles, **STOP**: report the hub and hand the
   YAML of step 5 to its administrators. If `wingman-mce-reader` does not
   exist, the 3.4 grant was never applied: do [3.3-to-3.4.md](3.3-to-3.4.md)
   step 5 first, with step 5's YAML below instead of its own. If it has rules
   other than the four of 3.4, **STOP**: do not overwrite it.
2. **Each hub answers at the address day1 uses.** A hub whose API is not
   `https://api.<mce>.<domain>:6443` shows as unreachable in live status
   today. For such a hub, do step 6.

## 5. Grant `list` on nodes and pods, on each MCE hub

First ask whether the account can already:

```bash
SA=system:serviceaccount:<sa-ns>:<sa>
oc auth can-i list nodes --as=$SA
oc auth can-i list pods --all-namespaces --as=$SA
oc auth can-i list agents.agent-install.openshift.io --all-namespaces --as=$SA   # the 3.4 grant
```

The third is the servers check's read (the free Agents of the needed
InfraEnvs). The 3.4 grant gives it; if it says `no`, the binding is not the
3.4 one: **STOP** and report it.

Both `yes`: skip this hub and record it. Otherwise save this as
`wingman-mce-reader.yaml` (the 3.4 ClusterRole with one more rule) and apply
it:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: wingman-mce-reader
rules:
  - apiGroups: [hypershift.openshift.io]
    resources: [hostedclusters, nodepools]
    verbs: [get, list]
  - apiGroups: [cluster.x-k8s.io]
    resources: [machines, machinesets]
    verbs: [get, list]
  - apiGroups: [capi-provider.agent-install.openshift.io]
    resources: [agentmachines]
    verbs: [get, list]
  - apiGroups: [agent-install.openshift.io]
    resources: [agents, infraenvs]
    verbs: [get, list]
  - apiGroups: [""]
    resources: [nodes, pods]
    verbs: [list]
```

```bash
oc apply -f wingman-mce-reader.yaml
oc auth can-i list nodes --as=$SA                         # yes
oc auth can-i list pods --all-namespaces --as=$SA         # yes
```

The ClusterRoleBinding of 3.4 is unchanged. If an answer is still `no`,
**STOP**: report the hub and `oc get clusterrolebinding wingman-mce-reader -o yaml`.
Repeat for every MCE that has a token.

## 6. Optional: a hub with its own API address

Only for a hub found in step 4.2. Rewrite the tokens Secret with that MCE in
the mapping form, without printing any token:

```bash
umask 077
kubectl -n <ns> get secret mce-sa-tokens -o jsonpath='{.data.tokens}' | base64 -d > tokens.yaml
```

Edit `tokens.yaml` (never `cat` it) so the entry reads:

```yaml
<mce>:
  token: <its token, as it was>
  url: https://<its API host>:<port>
```

The `url` is `https://<host>[:<port>]` with nothing after it; day1 refuses
anything else at start, naming the MCE. Then:

```bash
kubectl -n <ns> create secret generic mce-sa-tokens --from-file=tokens=tokens.yaml \
  --dry-run=client -o yaml | kubectl -n <ns> apply -f -
rm tokens.yaml
```

Use the Secret's name from `clusterStatus.tokensSecretName` if it is not
`mce-sa-tokens`. day1 reads the file at start; step 7 restarts it.

## 7. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

`day1.placementMinFreePods` needs no value (70); add
`--set day1.placementMinFreePods=<n>` only if the team chose another. With
an older Helm, use the values-file form of 3.3-to-3.4 step 7. If day1 does
not become ready and its log names the tokens file, step 6's edit is wrong:
roll back (step 9), fix `tokens.yaml`, and try again.

## 8. Verify

With a session token as in 3.3-to-3.4 step 8, for a site and env where
clusters are created:

```bash
SESSION=<the wingman-token cookie's value>
curl -s -o placement.json -w '%{http_code}\n' -H "Authorization: Bearer $SESSION" \
  "https://<route host>/api/day1/placement?site=<site>&env=prod&version=<a version the form offers>&need=<an InfraEnv>:1"
unset SESSION
```

`placement.json` holds no secret.

| Status | Means | Do |
|---|---|---|
| `200` | `candidates` lists the site's MCEs of that env, `pick` names one, `why` says why | For each candidate, the `readable` check is `pass` and `pods.free` is a number. Compare one with the hub: `oc get pods -A --field-selector=status.phase!=Succeeded,status.phase!=Failed -o wide` on the counted nodes |
| `200`, a `readable` check `fail` | its `detail` says why: "may not list nodes and pods" is step 5 for that MCE; "no token" is the tokens Secret; "unreachable" is the address (step 6) or the network | Fix that MCE; the others are not affected |
| `200`, a `servers` check `unknown` with "may not list Agents" | the token may not list Agents across the hub | Step 5's third `can-i` for that MCE |
| `200`, `spare` `null` everywhere | `server_scan_error` says why: server-scan is not configured, or not answering | Expected without `serverScan.url`; placement still picks on the rest |
| `501` | live status is off | Expected if step 3 found it off |
| `404` | no such site | Check the site folder's name |

Then open **New cluster** in the browser: after the site, env and version,
the form shows Wingman's pick and every candidate's numbers. **Do not create
a cluster to test**: Preview runs every check a create runs.

## 9. Roll back and report

- **Roll back:** `helm rollback <release> <revision from step 3> -n <ns>`.
  Nothing was written to GitLab. The extra grant is read-only and harmless to
  leave; to remove only it, apply the 3.4 ClusterRole of
  [3.3-to-3.4.md](3.3-to-3.4.md) step 5 again. A tokens Secret in the mapping
  form stops 3.9's day1 from starting: before rolling back, put every entry
  back in the plain form (`<mce>: <token>`), as in step 6.
- **Report:** the versions before and after; whether live status is on; per
  MCE, whether step 5 applied the grant or found it there, and both `can-i`
  answers; any MCE given its own address in step 6 (its name, never its
  token); `day1.placementMinFreePods`; and step 8's status with each
  candidate's `readable` check and `pick`. Never a token, `tokens.yaml` or
  `current-values.yaml`.
