# Upgrade: 3.2 → 3.3 (flavors v2)

For an agent inside the disconnected environment. Follow the steps in order.
Every check says what to do when it fails, and **STOP** means: change
nothing, finish the report (step 8) and hand it back.

Throughout, `<ns>`, `<release>`, `<registry>`, `<tag>` and `$CHART` mean what
they mean in [legacy-to-ecosystem.md](legacy-to-ecosystem.md); `<tag>` is
`3.3.0` or a later 3.3 release. `$DAY1` is the day1 values repo
(`gitops-day1/platform-config`), `$SPECS` the specs repo (`wingman/cluster-specs`),
both as checkouts at their default branch, read-only.

## 1. What changes

No setting, Secret or chart value changes. What changes is how Wingman reads
what is already in GitLab:

| Area | 3.2 | 3.3 |
|---|---|---|
| A flavor's locks | `immutable_paths`: a lock icon in the form, nothing enforced | `locked_paths`: the flavor's value is fixed. A create that sends another value is refused, and a later edit of the file shows as drift (ADR-0026). `immutable_paths` is still read, as `locked_paths`. |
| What can be locked | any path | the owners, `platform`, and per nodepool `replicas`, `configs`, `node_labels`; and the rule `nodepools[*].configs`, every nodepool (ADR-0029). A lock needs a value in `spec.day1.values`. |
| Machine configs | free text | checked against `mc-files/` in `$DAY1` at flavor save and at create, by the day1 CI's rule (ADR-0027). A name only in `mc-files/legacy/` is refused. The cluster's own network config is written `{name: nm-conf, hardware: <hw>}` and becomes `nm-conf-<clusterName>-<hw>`. |
| Nodepool defaults | — | optional `nodepool-defaults.yaml` in `$SPECS`: the configs a new nodepool starts with |
| Owners | any text | 1 to 10 digits (ADR-0028) |
| Drift | missing add-ons | missing add-ons, or a locked value the cluster file does not hold (ADR-0036) |
| New (admins) | — | import existing clusters into a flavor (one MR that writes only each file's header), and sync a cluster to its flavor (one MR per cluster; removals confirmed; ADR-0037) |

Nothing is written at upgrade. Import and sync only ever open MRs that a
person reviews and merges.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, exactly as in
[legacy-to-ecosystem.md](legacy-to-ecosystem.md) step 2.

## 3. Discover (read-only)

```bash
helm history <release> -n <ns>                       # the revision to roll back to
kubectl -n <ns> get deploy -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image
ls $DAY1/mc-files $DAY1/mc-files/templates           # the machine-config sources
ls $SPECS/specs                                      # the flavors
grep -n -A12 'immutable_paths\|locked_paths' $SPECS/specs/*.yaml
```

Record the running version (each image's tag). **STOP** if it is not a 3.2
release: upgrade to 3.2 first.

## 4. Check

1. **`mc-files/` is where Wingman reads it.** `$DAY1/mc-files/` exists, and
   each network template is `mc-files/templates/nm-conf-template-hw-<hw>.bu`.
   If there is no `mc-files/`, every config name is refused at save and
   create: **STOP**. If templates are named another way, they are not offered
   (3.3 lists each such file under `problems` in `GET /api/day1/machine-configs`):
   **STOP** and report the names.
2. **The CI resolves the name Wingman writes.** Find a cluster file whose
   nodepool has its own network config (`nm-conf-<clusterName>-<hw>`), and its
   last merged MR's pipeline in `$DAY1`. If that pipeline did not resolve the
   name to `templates/nm-conf-template-hw-<hw>.bu` (it failed on the name, or
   the team renames such configs by hand), **STOP** and report it: clusters
   created by 3.3 would fail the same way.
3. **Flavors with `immutable_paths`.** For each flavor from step 3 that lists
   paths, note them. In 3.3 each one is a lock only if it is lockable and has
   a value in `spec.day1.values`; otherwise the flavor still loads, the lock
   is not enforced, and the flavor shows a warning. Nothing to change before
   the upgrade; step 6 reads the warnings.
4. **Config names in flavors.** For each `configs` entry under
   `spec.day1.values` in `$SPECS/specs/*.yaml`, check that its `name` is a file
   in `mc-files/` (without `.bu`) outside `legacy/`, or `nm-conf` with a
   `hardware`. A flavor that names anything else can't be saved unchanged,
   and a create from it is refused until it is fixed. Record each one;
   it is not a stop condition.

## 5. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/instance=<release> --timeout=5m
```

Use the image value names your release's `$CHART/values.yaml` has, if they
differ from these.

## 6. Verify

With an admin session in the browser (or its token):

1. `GET /api/day1/machine-configs`: `static_configs` and `hardware_types`
   list what step 4.1 found, and `problems` is empty or names only files you
   expected not to be offered. `nodepool_defaults.found` is `false` unless
   the team has added the file (step 7).
2. **Flavors page:** every flavor loads. Open each flavor from step 4.3 and
   4.4; its warnings say which locks are not enforced and why. Fix them by
   editing the flavor (an MR to `$SPECS`), or record them for the team.
3. **Create a cluster, Preview only** (rule 5: never create a real cluster to
   test an upgrade) from one flavor with locks: the locked fields are
   read-only, each nodepool's configs come from the picker, and the preview
   shows `nm-conf-<clusterName>-<hw>` for the network config.
4. **Drift:** `GET /api/day1/clusters/drift-summary`. Clusters created from a
   flavor and edited by hand where it is now locked show as `drifted`. That is
   expected (step 1), not a failure; record how many.

## 7. Optional: nodepool defaults

If the team wants new nodepools to start with its usual configs, they add
`nodepool-defaults.yaml` to `$SPECS` by MR. The shape is in
`dev/gitlab-fixtures/wingman/cluster-specs/nodepool-defaults.yaml` of the
repository copy; use the team's own config names. It never changes an
existing flavor or cluster.

## 8. Roll back and report

- **Roll back:** `helm rollback <release> <revision from step 3> -n <ns>`. The
  upgrade itself wrote nothing to GitLab. Of the MRs merged since:
  - an imported cluster's header is the header 3.2 writes at create, and a
    synced file is an edit like any other: 3.2 reads both;
  - **a flavor saved by 3.3 does not load in 3.2**: 3.2 refuses the
    `locked_paths` field, so it lists that flavor with a load error and
    cannot create from it. Its network entries (`{name: nm-conf, hardware:
    <hw>}`) would also render as a literal `nm-conf` in 3.2. Before or right
    after rolling back, find them (`grep -l locked_paths $SPECS/specs/*.yaml`)
    and revert those MRs in `$SPECS`. Report each one.
- **Report:** the versions before and after, each check's result, the
  flavors with warnings (step 6.2) and config names that don't resolve (step
  4.4), and the drift count (step 6.4).
