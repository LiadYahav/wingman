# Upgrade: 3.51 → 3.52 (the Segments and Server Scan areas off by default)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 7) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.52.0` or a later 3.52 release.

## 1. What changes

The team keeps segments-manager and server-scan apart from Wingman for now
(the 2026-11-23 amendments of ADR-0047 and ADR-0048). Wingman's own pages
for them, the **Segments** area and the **Server Scan** area, are off unless
the deployment turns them on, and the top bar links to each system's own UI
instead.

| Area | 3.51 | 3.52, with the new values left out |
|---|---|---|
| An admin's top bar | Wingman · Segments · Server Scan, each opening the area inside Wingman | The same switch. **Segments** and **Server Scan** open segments-manager's and server-scan's own UIs in a new tab, with an external-link mark: `segmentsManager.uiUrl` and `serverScan.uiUrl`, else their `url`. Each shows only when its system is configured |
| `/segments`, `/server-scan` and their sidebars | Shown to admins | Not offered; a page opened by its address says the area is off |
| The Overview | Free Segments and Server Fleet Health, for admins | Neither card |
| A node's server, on the Nodes tab | Its page in Wingman's Server Scan area, for admins | Its page in server-scan's own UI, in a new tab |
| A server's name in Inventory Management | A link to its page in the Server Scan area, for admins | Text (as for a viewer before) |
| day1's `/api/day1/segments/*` and `/api/day1/server-scan/*` | As before | `501 FEATURE_DISABLED`, `details.setting` naming `DAY1_SEGMENTS_AREA` or `DAY1_SERVER_SCAN_AREA` |
| A viewer | No switch, no areas | Unchanged |
| Unchanged for everyone | | The cluster page's network card (EPG) and its links to segments-manager, the Nodes tab, MCE placement and Inventory Management: they read the same systems through their own routes |
| Chart | — | `day1.segmentsArea.enabled` (`DAY1_SEGMENTS_AREA`) and `day1.serverScanArea.enabled` (`DAY1_SERVER_SCAN_AREA`), both `false` by default; a new read, `GET /api/day1/platforms`. No new Secret, grant or metric |

**On upgrade an existing deployment loses the two areas**, because both
values default to `false`. To keep them as they were, set the two values
(step 4). The team decides; record which.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for any
release. Nothing else.

## 3. Discover (read-only)

```bash
# Prints only the two systems' url and uiUrl (no secret is among them)
helm get values <release> -n <ns> --all -o json | python3 -c \
  "import json, sys; v = json.load(sys.stdin); [print(k, {x: (v.get(k) or {}).get(x) for x in ('url', 'uiUrl')}) for k in ('segmentsManager', 'serverScan')]"
```

1. **Which systems are configured.** Record whether `segmentsManager.url`
   and `serverScan.url` are set. A system without its `url` had no area in
   3.51 and has no top-bar link in 3.52: nothing changes for it.
2. **Where each one's UI is.** Record `segmentsManager.uiUrl` and
   `serverScan.uiUrl`. Empty: the top bar links to `url`, the API's address,
   which people's browsers may not reach. If a configured system has no
   `uiUrl` and its `url` is an in-cluster Service (`*.svc`), ask the team
   for its UI's address and set it in step 4; without it the link leads
   nowhere for a browser.
3. **The team's decision.** Ask whether the admins keep the areas inside
   Wingman (both, one or neither). The default, neither, is what the team
   decided on 2026-11-23.

## 4. Change (only to keep an area, or to give a UI's address)

Add only the `--set`s you need to step 5's command:

```bash
--set day1.segmentsArea.enabled=true          # keep the Segments area (needs segmentsManager.url)
--set day1.serverScanArea.enabled=true        # keep the Server Scan area (needs serverScan.url)
--set segmentsManager.uiUrl=https://segments-manager.example   # its UI, for the top bar's link
--set serverScan.uiUrl=https://server-scan.example             # its UI, for the top bar's link
```

The chart refuses an area turned on without its system's `url`, naming
the value; day1 refuses to start so too.

## 5. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

## 6. Verify

1. `kubectl -n <ns> get configmap wingman-config -o yaml | grep -E '_AREA:'`
   shows `DAY1_SEGMENTS_AREA` and `DAY1_SERVER_SCAN_AREA` as step 4 chose
   (`"false"` without it).
2. Sign in as an admin. The top bar shows **Wingman**, then **Segments**
   and **Server Scan** for each configured system:
   - with its area off: an external-link mark; it opens the system's own UI
     in a new tab;
   - with its area on: it opens `/segments` or `/server-scan` inside
     Wingman, as in 3.51.
3. With the Server Scan area off: on a cluster's Nodes tab, a server's name
   opens server-scan's own server page in a new tab.
4. As a viewer, if you have one: no switch in the top bar.
5. The cluster page's network card still shows the EPG (with
   `segmentsManager.url`), and Inventory Management still counts each MCE's
   servers (with `serverScan.url`).

## 7. Roll back and report

Roll back with `helm rollback <release> <previous revision> -n <ns>`: 3.51
shows both areas to admins again, and ignores the two values. Wingman keeps
no state of its own, so nothing else is undone.

Report:
- the tag deployed;
- step 3's answers and the team's decision;
- the `--set`s of step 4, if any;
- step 6's results.
