# Upgrade: 3.52 → 3.53 (Scale on by default)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 7) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.53.0` or a later 3.53 release.

## 1. What changes

The platform's `update-nodepool` workflow is merged and runs in production,
so Wingman's **Scale** (ADR-0062) is on by default wherever Wingman has the
workflows orchestrator (ADR-0062's 2026-11-23 amendment). This release
changes only Scale's default: what Scale does while it is on is as in 3.52.

| Area | 3.52, with the default | 3.53, with the default |
|---|---|---|
| Scale on the Nodes tab | Off | **On wherever `workflows.url` is set.** For an admin each NodePool card has a − N + beside its ready count; without live status the same steppers sit on the **NodePool sizes** rows. A change asks first, then starts `update-nodepool` for that one NodePool, and its run shows in place |
| A scale | — | One commit by the workflow to day1 `main`, with no merge request, then an Argo CD sync of the cluster's Application. The approvals page does not see it; the cluster's History tab does |
| A scale-down | — | The confirmation asks which servers leave, one choice: the NodePool's own `redbull.io/scale-down-policy` (else CAPI picks at random), another policy for this run only, or the servers ticked (the list needs live status) |
| An edit (Edit cluster's YAML, a review edit of a pending merge request) | May change any NodePool's `replicas` | One that changes an existing NodePool's `replicas` is **refused** (422, nothing written) and points to Scale. A new cluster, a new `nodepool[]` entry with its first replicas, and removing an entry still work |
| A flavor's sync, a flavor rollout's per-cluster merge request | Write the flavor's locked replicas | Leave drifted locked replicas **out** of the merge request, list each NodePool (`held_replicas`) and offer **Restore with update-nodepool**, one run per cluster |
| A NodePool whose replicas its flavor locks | Edited like any other | Not scaled; only restored to its locked value |
| A merge request opened before the upgrade that changes replicas | — | Still merges (approving is not a write of the file); a review edit of it must put them back |
| Without `workflows.url` | No Scale; `day1.scaleNodepools.enabled: true` failed the render | No Scale, whatever the value says, and nothing fails: edits change replicas as before |
| Chart | `day1.scaleNodepools.enabled`, `false` by default | `true` by default. `DAY1_SCALE_NODEPOOLS` renders `"true"` only with `workflows.url`. No new value, Secret, grant or metric (`start_update_nodepool` exists since 3.40) |
| day1 | `DAY1_SCALE_NODEPOOLS=true` without `WORKFLOWS_API_URL` refused to start | Accepted: it means no Scale. The scale routes' `501` now says "DAY1_SCALE_NODEPOOLS=false, or no WORKFLOWS_API_URL" |

**On upgrade, a deployment with `workflows.url` gets Scale**, unless its
values set `day1.scaleNodepools.enabled: false`. Step 3 checks that the
platform can run it first. Without `workflows.url`, nothing in this release
changes anything: step 3.1 says so, and the rest is the generic upgrade.

**What Scale does not need:** live status, a hostedclusters-setup chart
change, or a specs-project template change. A NodePool's own scale-down
policy is another matter (step 3.5).

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for any
release. Nothing else for Wingman. The platform side (step 3) must already
be in place, or Scale stays off for now.

## 3. Discover and check (read-only)

1. **What the release sets now.**

   ```bash
   # Prints only workflows.url and day1.scaleNodepools (no secret is among them)
   helm get values <release> -n <ns> -o json | python3 -c \
     "import json, sys; v = json.load(sys.stdin); print('workflows.url:', (v.get('workflows') or {}).get('url')); print('day1.scaleNodepools:', (v.get('day1') or {}).get('scaleNodepools'))"
   ```

   Without `--all`, `helm get values` prints only the values the release
   sets, which are what `--reset-then-reuse-values` keeps. Record both lines.
   - `workflows.url` is `None` or empty: Wingman has no orchestrator, and
     Scale stays off whatever the value says. Skip steps 3.2 to 3.5 and step
     4, and go to step 5.
   - `day1.scaleNodepools` is `{'enabled': False}`: the release turns Scale
     off, and it stays off after the upgrade. A values file copied from an
     older chart's `values.yaml` does this too, without anyone choosing it.
     Ask the team whether to turn Scale on, and record their answer. If yes,
     do steps 3.2 to 3.4 first, then step 4's `true`.
   - `None` (not set) or `{'enabled': True}`: Scale turns on at the upgrade.
     Do steps 3.2 to 3.4 before step 5.
2. **The orchestrator has update-nodepool.** From a day1 pod, with
   `<workflows.url>` from step 3.1:

   ```bash
   kubectl -n <ns> exec deploy/wingman-day1 -- python -c \
     "import urllib.request as u, json; d = json.load(u.urlopen('<workflows.url>/openapi.json', timeout=5)); print('/workflows/server-lifecycle/update-nodepool' in d['paths'])"
   ```

   - `True`: go on.
   - No answer, or an error: **STOP**. Day1 can't reach the orchestrator.
     Don't add a network policy to fix it.
   - `False`: this orchestrator has no update-nodepool. **Keep Scale off**:
     add step 4's `false` to step 5 and record why. With Scale on and no
     workflow, every scale and Restore says "update-nodepool is not
     deployed on this orchestrator yet", and nobody can change an existing
     NodePool's replicas from Wingman: an edit of them is refused, a sync
     leaves them out. If the team wants Scale on anyway, **STOP** and
     report: that is their decision to make
     ([3.39-to-3.40.md](3.39-to-3.40.md) step 3.1 lists what still works).
3. **Every MCE's server-lifecycle worker can run it.** The workflow runs
   every call on the MCE's own worker. On each MCE that runs hosted
   clusters, the `server-lifecycle-worker` release must:
   - be from the workflows release that has update-nodepool, the one the
     orchestrator runs or a later one:
     `kubectl -n <worker ns> get deploy -o jsonpath='{..image}'`, compared
     with the release the platform team deployed;
   - have `day1.repoUrl` set to **the same day1 repo Wingman reads**, and
     its push token (`DAY1_GIT_TOKEN`, from the credentials Secret or
     `day1.tokenSecret`: check the Secret exists by name, never print it);
   - have `rbac.hostedClusters: true` (Machines, NodePools, the hosted
     cluster's admin kubeconfig), and `argo.namespace` set to where the
     hosted clusters' Argo CD Applications live;
   - reach the day1 Git server.

   ```bash
   # On each MCE, with its kubeconfig; prints only these three values
   helm get values <worker release> -n <worker ns> --all -o json | python3 -c \
     "import json, sys; v = json.load(sys.stdin); print('day1.repoUrl:', (v.get('day1') or {}).get('repoUrl')); print('rbac.hostedClusters:', (v.get('rbac') or {}).get('hostedClusters')); print('argo.namespace:', (v.get('argo') or {}).get('namespace'))"
   ```

   Without these, a scale of that MCE's clusters fails at its first call
   with nothing written (`Day1NotConfiguredError`), or waits for a worker
   that never picks it up. If any MCE is not ready, **keep Scale off**
   (step 4's `false`) and record which MCEs, or **STOP** if the team wants
   it on anyway.
4. **The team knows who writes replicas now.** While Scale is on, no Wingman
   merge request changes an existing NodePool's replicas: the workflow
   commits them straight to day1 `main` and has Argo CD apply them (step 1's
   table). A team that sized clusters by editing the file, or by syncing a
   flavor, now uses Scale, or Restore for a flavor's locked value. Record in
   the report that the team was told.
5. **A NodePool's own scale-down policy (optional; it does not block).**
   Wingman reads a nodepool's `redbull.io/scale-down-policy` from its
   entry's `annotations` in the day1 file, and the create form, a flavor and
   Edit cluster write it there. It reaches the NodePool, where
   update-nodepool reads it, only if the hostedclusters-setup chart renders
   a nodepool entry's `annotations`: that is **patch 0001** in
   [patches/hostedclusters-setup/](patches/hostedclusters-setup/README.md).
   Check your chart copy's `templates/nodepool.yaml` for it, and record
   whether it is there. Without it:
   - Scale works, and a scale-down picks by a policy set by hand on the
     NodePool, else CAPI at random;
   - the annotation in the file does nothing, and the confirmation names a
     policy the NodePool does not have.

   A policy for one run and picking the servers need no chart change.
   `least-utilized` needs the metrics API on the hosted cluster, or its run
   fails (`NodeMetricsUnavailableError`).

## 4. Change (only to choose Scale's state against the default)

Add at most one of these to step 5's command:

```bash
--set day1.scaleNodepools.enabled=false   # keep Scale off (step 3.2 or 3.3 not ready, or the team's choice)
--set day1.scaleNodepools.enabled=true    # turn it on where the values set false (step 3.1), after steps 3.2 to 3.4
```

Without either, the release keeps what it sets, else takes the new default
(on, with `workflows.url`).

## 5. Upgrade

```bash
helm history <release> -n <ns> | tail -3          # note the current revision, for a rollback
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

Add step 4's line, if any, to the `helm upgrade`. Use
`--reset-then-reuse-values`, not `--reuse-values`: `--reuse-values` keeps
3.52's computed default, `false`, so Scale would stay off without anyone
saying so. With Helm older than 3.14, pass the release's values as a file
instead (step 7 of [3.3-to-3.4.md](3.3-to-3.4.md)): a file that holds
`scaleNodepools.enabled: false` keeps Scale off.

## 6. Verify

1. `kubectl -n <ns> get configmap wingman-config -o yaml | grep DAY1_SCALE_NODEPOOLS`
   prints `"true"` with `workflows.url` and Scale not turned off, else
   `"false"`.
2. The pods are ready with no restarts
   (`kubectl -n <ns> get pods -l app.kubernetes.io/part-of=wingman`), and
   `kubectl -n <ns> logs deploy/wingman-day1 | grep -c Traceback` prints `0`.
3. With a session token as in 3.3-to-3.4's step 8, for any cluster:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $SESSION" \
     "https://<route host>/api/day1/clusters/<cluster>/scale"
   ```

   `200` means Scale is on; `501` means it is off. It must match step 1.
4. With Scale on, as an admin, open a cluster's Nodes tab: each NodePool
   card (or **NodePool sizes** row, without live status) has a − N +.
   **Don't scale a cluster to test it**: a scale is a real commit to day1
   `main`, applied by Argo CD. Run a first real scale only when the team
   asks for one, and record its run.
5. With Scale on (optional): in Edit cluster, change one existing
   NodePool's `replicas` and submit. It is refused, pointing to Scale, and
   nothing is written. Leave without saving.

## 7. Roll back and report

Roll back Scale alone with step 5's command and
`--set day1.scaleNodepools.enabled=false`: edits and flavor syncs change
replicas again, as in 3.52. Or roll back the release with
`helm rollback <release> <previous revision> -n <ns>`: 3.52 comes back with
the values it had, so Scale is as it was before (off unless they turned it
on). Wingman keeps no state of its own. Scales already made are commits in
day1 `main` and stay there; a rollback does not undo them.

Report:
- the tag deployed;
- step 3.1's two lines, and the team's answer if Scale was off;
- step 3.2's answer, and step 3.3's per MCE;
- that the team was told who writes replicas (step 3.4), and whether patch
  0001 is in the chart (step 3.5);
- step 4's `--set`, if any;
- step 6's results.
