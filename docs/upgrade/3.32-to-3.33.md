# Upgrade: 3.32 → 3.33 (chart hardening: UBI nginx, restricted pods, a values schema)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 8) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.33.0` or a later 3.33 release.
`<mirror>` is the registry the cluster pulls Wingman's images from.

## 1. What changes

| Area | 3.32 | 3.33 |
|---|---|---|
| nginx's image | `nginx:latest` by default, or the release's own `image.nginx` | Red Hat's UBI nginx, `registry.access.redhat.com/ubi9/nginx-124:9.8`, pulled by its digest `sha256:d5cec86a9adf972dbfa0d87b134e7c404706cc1920fc2e6a2b146e290276f219` (ADR-0058). **One more image to mirror** |
| nginx | probed on `/`, through the web; HTML 502 and 504 pages | answers `/healthz` itself, for liveness and readiness; its own 502, 503 and 504 on `/api/` are `application/problem+json` (`DEPENDENCY_UNAVAILABLE`, naming day1 or day2); logs to stdout and stderr; no version shown. Paths, timeouts, gzip and the live-status stream are unchanged |
| Pods | `runAsNonRoot` | also the RuntimeDefault seccomp profile, no capabilities, no privilege escalation, a read-only root, and no service-account token mounted. Writable: nginx's `/tmp` and the web's `.next/cache`, as `emptyDir`s. All of it fits `restricted-v2`: no SCC to grant |
| Values | any key, any type; image tags default to `latest` | `values.schema.json`: an unknown key, a wrong type or a value out of range fails the render, naming the key (ADR-0059); keys older releases dropped are still accepted. `image.{day1,day2,web}.tag` has no default: an empty one fails |

GitLab, the Secrets, the Route and the Services do not change, and nothing is
written to GitLab.

## 2. What to bring in from the connected side

- The three images of `<tag>` and the repository at `v<tag>`, as for 3.32.
- The UBI nginx image, by digest and with every architecture, unless the
  cluster already pulls `registry.access.redhat.com` through an
  `ImageDigestMirrorSet` (step 3 checks):

  ```bash
  skopeo copy --all \
    docker://registry.access.redhat.com/ubi9/nginx-124:9.8@sha256:d5cec86a9adf972dbfa0d87b134e7c404706cc1920fc2e6a2b146e290276f219 \
    docker://<mirror>/ubi9/nginx-124:9.8
  ```

  `--all` keeps the manifest list, so the digest stays the chart's.

## 3. Discover (read-only)

```bash
helm list -n <ns>                                   # the release and its chart
helm history <release> -n <ns>                      # the revision to roll back to
kubectl -n <ns> get deploy -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image
helm get values <release> -n <ns> -o yaml | grep -A16 '^image:'   # the release's own image values; no secrets
kubectl get imagedigestmirrorset -o yaml | grep -B2 -A4 'registry.access.redhat.com'   # OpenShift; may be empty
helm version --short
```

Record:

1. **The running version** (each Wingman image's tag). **STOP** if it is not a
   3.32 release: do the guides on the way first ([README](README.md),
   "Skipping versions").
2. **`image.registry`**: empty, or the prefix of every image.
3. **`image.nginx`** in the release's own values: absent (the chart's default
   was used), or its `repository` and `tag`.
4. **How nginx will be pulled**, from 2 and the mirror set:
   - `image.registry` set: from `<registry>/<image.nginx.repository>`. Step 5
     sets the repository to the mirror's path (`ubi9/nginx-124`, as copied in
     step 2).
   - `image.registry` empty and an `ImageDigestMirrorSet` for
     `registry.access.redhat.com`: the chart's default works as is.
   - `image.registry` empty and the cluster reaches `registry.access.redhat.com`:
     the default works.
   - Otherwise: set `image.nginx.repository` to the image's full path in the
     mirror (`<mirror>/ubi9/nginx-124`).

Check that the image is there by its digest (read-only):

```bash
oc image info <the repository from 4>@sha256:d5cec86a9adf972dbfa0d87b134e7c404706cc1920fc2e6a2b146e290276f219 --filter-by-os=linux/amd64
```

It prints the image (nginx 1.24, `USER 1001`): go on. "not found" or
"unauthorized": **STOP**; mirror it (step 2) or fix the pull secret
(`imagePullSecret`) first.

## 4. Check the values against the new chart (read-only)

A dry run of the real upgrade, with the release's values as they will be
reused. Its manifest holds the rendered Secret, so throw it away:

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag> \
  --dry-run=client > /dev/null
```

No output and exit 0: go to step 5. Otherwise each line names a key; no secret
value is printed (no secret key has a pattern). Handle each, and note it for
step 6 and the report:

| Error | Means | Do |
|---|---|---|
| `at '/<path>': additional properties '<key>' not allowed` | a key the chart does not read | A typo of a real key (compare with `$CHART/values.yaml`): set the real key to its value and drop the typo, `--set <path>.<key>=null`. It never worked, so say in the report what it was meant to do. A key no release reads: `--set <path>.<key>=null`. A key that looks like something the team relies on and is in no `values.yaml`: **STOP** |
| `at '/serverScan/sslVerify': got boolean, want string` (or `workflows`, `segmentsManager`) | a boolean the chart turned into `"true"` before 3.33: verification was on | Keep what runs: `--set-string <path>=true`. Turning it off is the team's decision, not the upgrade's |
| `at '/<path>': got …, want …`, `value must be one of …`, `maximum`, `minimum`, `does not match pattern` | a value of the wrong type or out of range | **STOP**: the value did not do what it says; find out what it was meant to be |
| `image.<name>.tag is empty` | a tag missing from the command | Add `--set image.<name>.tag=<tag>` |
| `image.nginx.tag is "<x>" but image.nginx.digest is the chart's` | the release names another nginx (step 3, 3): its tag beside the chart's digest would pull nothing | Step 5 |

Keys older releases dropped (`quickLinks.status`, `quickLinks.sslVerify`,
`quickLinks.argocdTokensSecret`, `cache`, `paths`, `gitlab.defaultBranch`,
`gitlab.sslVerify`, `clusterStatus.clusterNamePrefix`) pass: they are ignored.
Delete them when convenient, with `--set <key>=null`.

An older Helm may word schema errors differently (`Additional property <key>
is not allowed`); they name the same keys. With Helm older than 3.14,
check the values file of step 6's second form with `helm template <release>
$CHART -n <ns> -f current-values.yaml --set ... > /dev/null` instead.

Repeat the dry run with the `--set` lines you added until it passes.

## 5. Choose nginx's image

| Step 3 found | Set (beside step 4's lines) |
|---|---|
| no `image.nginx` in the release's values, `image.registry` empty, the image pullable as is | nothing |
| no `image.nginx`, `image.registry` set | `--set image.nginx.repository=ubi9/nginx-124` |
| an `image.nginx` of another nginx (the dry run's last error) | the UBI image: `--set image.nginx.repository=<registry.access.redhat.com/ubi9/nginx-124, or its path in the mirror> --set-string image.nginx.tag=9.8`. The chart's digest then applies |
| the team wants to keep that other nginx | `--set image.nginx.digest=` (pulled by its tag, as before). It must be nginx 1.19.5 or later (the chart starts it with `-e`) and run as non-root; 3.33 is checked only with the UBI image. Record why in the report |

Run step 4's dry run once more with these lines: it must pass.

## 6. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag> \
  <the --set lines of steps 4 and 5>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

With Helm older than 3.14, pass the release's values as a file, as in
[3.3-to-3.4.md](3.3-to-3.4.md) step 7, with the same `--set` lines.

A pod that does not start: `kubectl -n <ns> describe pod <pod>` and its log.
`ImagePullBackOff` on nginx: the image is not where step 3 found it; roll back
(step 8) and recheck step 3. `CreateContainerConfigError` with
`runAsNonRoot`: the image runs as root (step 5's last row); roll back.

## 7. Verify

```bash
kubectl -n <ns> get pods -l app.kubernetes.io/part-of=wingman \
  -o custom-columns=NAME:.metadata.name,READY:.status.containerStatuses[*].ready,SCC:.metadata.annotations.openshift\.io/scc
kubectl -n <ns> get deploy wingman-nginx -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
curl -sS https://<route host>/healthz                  # ok
kubectl -n <ns> logs deploy/wingman-nginx --tail=5     # the requests, one per line
kubectl -n <ns> logs deploy/wingman-web | grep -c -i -E 'EROFS|EACCES'    # 0
```

Every pod ready, each admitted by `restricted-v2` (a pod under another SCC
means its service account was granted one: report it, it is not needed);
nginx's image is the one step 5 chose, with the digest unless you emptied it.
Then open Wingman, sign in, and open the cluster list and one cluster. A
`DEPENDENCY_UNAVAILABLE` there that names day1 or day2 is nginx saying that
service has no ready pod: check that pod.

## 8. Roll back and report

Roll back with `helm rollback <release> <revision from step 3> -n <ns>`: 3.32's
nginx, probes and pod settings come back with it, and Wingman keeps no state
of its own. Report: the tag deployed; the nginx image running (repository, tag,
digest) and why (step 5's row); each key step 4 changed or removed, by name
only; the SCC column; step 7's results.
