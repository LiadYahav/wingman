# Upgrade: 3.53 → 3.54 (Inventory follows the naming convention)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 6) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.54.0` or a later 3.54 release, from any
3.53 release (3.53.0, or 3.53.1: docs only).

## 1. What changes

The platform's naming convention (2026-11-22) names an InfraEnv
`<flavor>-<mtl|kv<cpu>>-<zone>` (`c200-mtl-az1`) and gives it the
`spec.agentLabels` `redbull.io/flavor`, `redbull.io/size`, `redbull.io/site`
and `topology.kubernetes.io/zone`; a server is
`ocp-<flavor>-<mtl|kv<cpu>>-<site>-<serial>`. The platform's workflows
follow it, and this release makes Wingman follow the workflows. No value,
Secret, grant or metric is new: the only Wingman step is the generic
upgrade. The checks below tell the team what the pages will show.

| Area | 3.53 | 3.54 |
|---|---|---|
| Inventory Management: a pool's servers | The free servers named `ocp-<InfraEnv name>…` | The free servers named `ocp-<flavor>-<size>-<site>-…`, from the InfraEnv's three labels: what `add-server-to-mce`'s pool draw asks server-scan for since the workflows' commit `29ef001` (2026-11-22). No zone: the InfraEnvs of one flavor in several zones list the same servers |
| An InfraEnv without those labels | Listed like any other | Marked on its row; the install dialog says the workflow would refuse a pool draw into it (`InfraEnvAgentLabelsError`). A named install still works |
| Live status off, or an MCE unreadable | Pools from the day1 files, servers matched by the InfraEnv's name | Pools from the day1 files, no server counted ready, and a pool's list is every free server, said so: Wingman cannot read the labels |
| A free Agent's pool on an MCE's card | The InfraEnv its name starts with | The one InfraEnv whose labels name it, else its lock's, else **No single InfraEnv** (a server named before the convention fits none) |
| A named install | Refused (422) for a server not named `ocp-<InfraEnv>…` | Any free server that is not locked, in maintenance or contested: the workflow does not match a named server to the pool |
| The uninstall confirmation | "then out of the MCE … server-scan shows it free" | The server stays in the MCE, a free Agent in its InfraEnv; leaving the MCE is `remove-server-from-mce` (uninstall-server-from-hc since 2026-11-19) |
| The MCE read | InfraEnv names | The same list call, with each InfraEnv's `spec.agentLabels`: no new grant |

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for any
release. Nothing else for Wingman. The platform side is step 3's to check.

## 3. Discover and check (read-only)

1. **Which workflows release runs here.** Wingman 3.54 describes the
   workflows of team-redbull/workflows `main` at `29ef001` (2026-11-22) or
   later: add-server-to-mce draws by the InfraEnv's labels, and
   uninstall-server-from-hc (since 2026-11-19) ends at a free Agent.

   ```bash
   # The orchestrator's and the server-lifecycle workers' images (no secret among them)
   kubectl -n <workflows ns> get deploy -o jsonpath='{range .items[*]}{.metadata.name}{"  "}{..image}{"\n"}{end}'
   # On each MCE, with its kubeconfig
   kubectl -n <worker ns> get deploy -o jsonpath='{range .items[*]}{.metadata.name}{"  "}{..image}{"\n"}{end}'
   ```

   Compare each image with the release the platform team deployed, and
   record them. The workflow logic and each MCE's worker both matter: a
   worker that predates the labels draws by the InfraEnv name's first three
   words instead.
   - All from 2026-11-22 or later: go on.
   - Older: Wingman 3.54 still works, but its Inventory describes the newer
     draw, and its uninstall confirmation the newer end. Record it, tell
     the team, and ask whether to upgrade Wingman now or after the
     workflows. If they say wait, **STOP**.
2. **Which InfraEnvs carry the labels.** On each MCE, list every InfraEnv
   with the three labels a pool draw needs:

   ```bash
   # Namespace, name, flavor, size, site; a "-" is a missing label
   kubectl get infraenv -A -o json | python3 -c \
     "import json, sys; ks = ('redbull.io/flavor', 'redbull.io/size', 'redbull.io/site'); [print(i['metadata']['namespace'], i['metadata']['name'], *[((i.get('spec') or {}).get('agentLabels') or {}).get(k, '-') for k in ks]) for i in json.load(sys.stdin)['items']]"
   ```

   A `-` is a missing label: with step 3.1's release the workflow refuses a
   pool draw into that InfraEnv (herzi's included), and Wingman 3.54 marks
   it. Each value must be one lowercase word of letters and digits (a site
   `bat-yam` is refused too). Record the InfraEnvs that lack a label and
   tell the team; adding labels is the platform team's change, never this
   upgrade's. Nothing here blocks the upgrade.
3. **Live status.** `helm get values <release> -n <ns> -o json` shows
   `clusterStatus.enabled`. Without it, Inventory cannot read the labels:
   its pools count no ready server and list every free server. Record it;
   it is not a reason to stop.

## 4. Upgrade

The generic upgrade ([README](README.md#the-generic-upgrade-no-guide)):

```bash
helm history <release> -n <ns> | tail -3          # note the current revision, for a rollback
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

## 5. Verify

1. The pods are ready with no restarts
   (`kubectl -n <ns> get pods -l app.kubernetes.io/part-of=wingman`), and
   `kubectl -n <ns> logs deploy/wingman-day1 | grep -c Traceback` prints `0`.
2. With a session token as in 3.3-to-3.4's step 8:

   ```bash
   # Each pool's name prefix, or why it has none (prints no server and no secret)
   curl -s -H "Authorization: Bearer $SESSION" "https://<route host>/api/day1/inventory" | python3 -c \
     "import json, sys; [print(m['mce'], p['infra_env'], p['server_prefix'], '; '.join(p['label_problems'])) for m in json.load(sys.stdin)['mces'] for p in m['pools']]"
   ```

   With live status, every InfraEnv step 3.2 found labelled prints its
   `ocp-<flavor>-<size>-<site>-`, and every one it found lacking prints
   `None` and the missing labels. Without live status every prefix is
   `None` and no problem is listed.
3. As an admin, open Inventory Management: an InfraEnv that lacks a label
   has a warning mark on its row. **Don't install a server to test it**:
   an install is a real run on the platform.

## 6. Roll back and report

`helm rollback <release> <previous revision> -n <ns>` brings 3.53 back:
Inventory matches by the InfraEnv's name again. Wingman keeps no state of
its own, and this release writes nothing.

Report:
- the tag deployed and the revision rolled back to, if any;
- step 3.1's images, and whether they are from 2026-11-22 or later;
- step 3.2's InfraEnvs that lack a label, per MCE, and that the team was
  told;
- whether live status is on (step 3.3);
- step 5's results.
