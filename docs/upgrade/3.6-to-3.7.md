# Upgrade: 3.6 → 3.7 (create through the provision-cluster workflow, optional)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 6) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.7.0` or a later 3.7 release.

## 1. What changes

| Area | 3.6 | 3.7 |
|---|---|---|
| Create a cluster | Wingman commits the file on a branch and opens the merge request; CI runs allocate-segment on the branch | The same by default. With `day1.provisioner: workflow`, Wingman renders and checks the file as before and then starts the platform's `provision-cluster` workflow, which reserves the segment, pushes the file on its own branch, opens the merge request and waits for it. The create page shows the run: its phase, its merge request, its error (ADR-0042) |
| Modify, delete, sync, import | Wingman's merge requests | Unchanged |
| Chart | — | `day1.provisioner` (`merge-request` by default). `workflow` needs `workflows.url` (which already needs `serverScan.url`); the chart refuses to render without it |
| Metrics | — | `workflows` gains the operation `start_provision` (`docs/ops/metrics.md`) |

With the default, nothing changes and there is nothing to do but the image
tags. The rest of this guide is for turning the workflow on.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for 3.6.

## 3. Check before turning it on (read-only)

1. **The orchestrator has the workflow.** From a day1 pod:

   ```bash
   kubectl -n <ns> exec deploy/wingman-day1 -- python -c \
     "import urllib.request as u, json; d = json.load(u.urlopen('<workflows.url>/openapi.json', timeout=5)); print('/workflows/cluster-lifecycle/provision-cluster' in d['paths'])"
   ```

   `True`: go on. `False`, or no answer: **STOP**. The orchestrator is older
   than the workflow, or day1 can't reach it. Don't add a network policy to
   fix it.
2. **The team agrees.** In `workflow` mode, the workflow opens the merge
   request, not Wingman. Wingman's approvals page and the cluster list's
   pending rows don't show it until it is merged
   (`docs/notes/2026-11-12-provision-cluster-workflow-api.md`, open
   questions). Record in the report that the team chose this. From 3.14.0
   the approvals page lists it, marked as the workflow's, and it is
   reviewed and merged in GitLab (ADR-0042's amendment).

## 4. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag> \
  --set day1.provisioner=workflow          # leave this line out to keep merge requests
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

The render fails with "day1.provisioner workflow needs workflows.url" when
the release has no `workflows.url`: set it as in 3.3-to-3.4's step 6, or
leave the workflow off.

## 5. Verify

With a session token as in 3.3-to-3.4's step 8:

```bash
curl -s -H "Authorization: Bearer $SESSION" "https://<route host>/api/day1/clusters/provisioner"
```

`{"mode":"workflow"}` (or `merge-request` if you left it off). Don't create
a cluster to test it: a create in `workflow` mode starts a real provision.
The first real create shows its run on the create page. Its merge request
is the workflow's.

## 6. Roll back and report

Roll back the mode alone with `--set day1.provisioner=merge-request`, or
the release with `helm rollback <release> <previous revision> -n <ns>`; 3.6
ignores the new key. Report: the tag deployed, the mode, step 3's answers
and step 5's answer.
