# Upgrade: 3.55 → 3.56 (every create starts provision-cluster)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 7) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.56.0` or a later 3.56 release.
`<workflows ns>` is the namespace of the platform's workflows orchestrator and
its `cluster-lifecycle-worker` (the hub's), and `<route host>` is Wingman's.

## 1. What changes

Since 3.7.0 (ADR-0042) a create could either open Wingman's own merge request
(`day1.provisioner: merge-request`, the default) or start the platform's
`provision-cluster` workflow (`workflow`). The merge-request create no longer
works on the current platform: since workflows commit `ff1aba7`
allocate-segment writes nothing to Git, so such a merge request never gets its
`vlanId` and `dhcp_values`. `provision-cluster` reserves the segment itself.
This release makes the workflow the only way to create, makes the
orchestrator a required dependency, and removes the merge-request create
(ADR-0042's 2026-11-23 amendment).

| Area | 3.55, with `day1.provisioner: workflow` | 3.56 |
|---|---|---|
| Create a cluster | Starts `provision-cluster` with the rendered file; the page shows the run | The same. There is no other way |
| Create with `day1.provisioner: merge-request` | Wingman's own merge request | Gone |
| `workflows.url` | Needed for `workflow` | **Required.** The chart refuses to render without it unless `environment: development`, and day1 refuses to start in production without `WORKFLOWS_API_URL`. It still needs `serverScan.url` (the uninstall's rule since 3.4) |
| `day1.provisioner` | `merge-request` or `workflow` | Deprecated: accepted, ignored, renders nothing. Delete it (step 4) |
| `DAY1_PROVISIONER` in `wingman-config` | Set | Not rendered, and nothing reads it |
| `GET /api/day1/clusters/provisioner` | `{"mode": ...}` | `404` |
| An open create merge request Wingman opened before | Holds its name; counted by placement | Not counted: only the workflow's merge requests, on `provision-cluster/<stem>`, hold a name and count. Step 3.5 checks there are none |
| Edit, delete, sync, import, flavor rollouts, flavors, day2 | Wingman's merge requests | Unchanged |
| The workflow's merge request on Approvals | Listed, marked, reviewed in GitLab | Unchanged |

No new Secret, grant, network rule or metric. The create's metric operation
`start_provision` exists since 3.7.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for any
release. Nothing else for Wingman. The platform's `provision-cluster`
(orchestrator and `cluster-lifecycle-worker`) must already run here: step 3
checks it.

## 3. Discover and check (read-only)

Do every check before step 4. If any one fails, **STOP**: this release
cannot create clusters there, and Wingman refuses to start without the
orchestrator.

1. **`workflows.url` is set.**

   ```bash
   # Prints only these values (no secret is among them)
   helm get values <release> -n <ns> -o json | python3 -c \
     "import json, sys; v = json.load(sys.stdin); w = v.get('workflows') or {}; s = v.get('serverScan') or {}; d = v.get('day1') or {}; print('workflows.url:', w.get('url')); print('serverScan.url:', s.get('url')); print('day1.provisioner:', d.get('provisioner'))"
   ```

   Record the three lines. `workflows.url` empty or `None`: **STOP**. (A
   release that sets `workflows.url` already has `serverScan.url`: 3.55's
   chart refuses one without the other.)
2. **Creates already start the workflow.** Step 3.1's `day1.provisioner`
   line must be `workflow`. `merge-request` or `None` (the default,
   `merge-request`): **STOP**, and report it. The team creates clusters by
   Wingman's merge request today and must switch first, on 3.55, with
   [3.6-to-3.7.md](3.6-to-3.7.md)'s steps; run this guide after that.
3. **The orchestrator has provision-cluster.** From a day1 pod, with
   `<workflows.url>` from step 3.1:

   ```bash
   kubectl -n <ns> exec deploy/wingman-day1 -- python -c \
     "import urllib.request as u, json; d = json.load(u.urlopen('<workflows.url>/openapi.json', timeout=5)); print('/workflows/cluster-lifecycle/provision-cluster' in d['paths'])"
   ```

   `True`: go on. `False`, no answer or an error: **STOP**. Don't add a
   network policy to fix a connection.
4. **The workflow writes to the day1 project Wingman reads.** The
   `cluster-lifecycle-worker` reads `DAY1_REPO_URL` from its ConfigMap
   `cluster-lifecycle-config`; the `sed` drops anything before an `@`, so no
   credential is printed:

   ```bash
   kubectl -n <workflows ns> get configmap cluster-lifecycle-config \
     -o jsonpath='{.data.DAY1_REPO_URL}' | sed -E 's#//[^/@]*@#//#'; echo
   ```

   Then Wingman's day1 project, with a session token as in 3.3-to-3.4's
   step 8 and any cluster `<cluster>` Wingman lists:

   ```bash
   curl -s -H "Authorization: Bearer $SESSION" \
     "https://<route host>/api/day1/clusters/<cluster>" | python3 -c \
     "import json, sys; print(json.load(sys.stdin)['gitlab_url'].split('/-/blob/')[0])"
   ```

   The first line, without a trailing `.git`, must be the second: the same
   GitLab host and the same project path. Different: **STOP**, and report
   both: the workflow would push new clusters where Wingman does not look.
5. **No create merge request of Wingman's own is still open.** In GitLab,
   the day1 project's open merge requests with the labels `wingman` and
   `create` (titles `[Wingman/Day1] Create cluster …`). Or, with the session
   token:

   ```bash
   curl -s -H "Authorization: Bearer $SESSION" "https://<route host>/api/day1/approvals" | \
     python3 -c "import json, sys; print([m['web_url'] for m in json.load(sys.stdin) if m['title'].startswith('[Wingman/Day1] Create cluster')])"
   ```

   `[]`: go on. Any: **STOP** and report their links. They predate the
   switch to the workflow and have no segment from it; after the upgrade
   Wingman no longer counts them, so a second create of the same name would
   not be refused. The team merges (once each file has its `vlanId` and
   `dhcp_values`) or closes each one first.

## 4. Change

`day1.provisioner` is ignored from now on. Delete it from the release's
values with step 5's `--set day1.provisioner=null`, and from any values file
kept for this release. Nothing else.

## 5. Upgrade

```bash
helm history <release> -n <ns> | tail -3          # note the current revision, for a rollback
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag> \
  --set day1.provisioner=null
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

The render fails with "workflows.url is required" when the release has no
`workflows.url`: step 3.1 should have stopped you. With Helm older than 3.14,
pass the release's values as a file instead (step 7 of
[3.3-to-3.4.md](3.3-to-3.4.md)), without `day1.provisioner`.

## 6. Verify

1. `kubectl -n <ns> get configmap wingman-config -o yaml | grep -E 'DAY1_PROVISIONER|WORKFLOWS_API_URL'`
   prints only the `WORKFLOWS_API_URL` line.
2. The pods are ready with no restarts
   (`kubectl -n <ns> get pods -l app.kubernetes.io/part-of=wingman`), and
   `kubectl -n <ns> logs deploy/wingman-day1 | grep -c Traceback` prints `0`.
3. With the session token:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $SESSION" \
     "https://<route host>/api/day1/clusters/provisioner"
   unset SESSION
   ```

   prints `404`: the mode route is gone.
4. As an admin, open **Clusters → Create**, fill the form for a name nobody
   uses and press **Review & Create**. The review shows the file and says
   "This is the file the provision-cluster workflow receives", and its button
   reads **Confirm — Start provision-cluster**. **Close the dialog: don't
   confirm.** A confirmed create starts a real run that reserves a segment
   and opens a merge request. The review ran every check a create runs and
   wrote nothing.

## 7. Roll back and report

Roll back with `helm rollback <release> <previous revision> -n <ns>`: 3.55
comes back with the values it had, `day1.provisioner: workflow` included, and
creates start the workflow as before. Wingman keeps no state of its own.
Runs started and merge requests the workflow opened stay as they are.

Report:
- the tag deployed;
- step 3.1's three lines;
- steps 3.3, 3.4 (both lines) and 3.5's results;
- step 6's results.
