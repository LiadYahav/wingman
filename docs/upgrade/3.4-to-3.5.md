# Upgrade: 3.4 → 3.5 (a cluster's EPG from segments-manager)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 6) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.5.0` or a later 3.5 release.

## 1. What changes

| Area | 3.4 | 3.5 |
|---|---|---|
| The cluster page's "HostedCluster & network" card | VLAN and DHCP network from the cluster file; a link to segments-manager | VLAN and **Segment** (`dhcp_values.network` as its /24) from the cluster file, as before: Git is the source of truth. New: the **EPG** segments-manager records for that segment, and a warning when segments-manager disagrees with the file (another VLAN, another cluster, not Allocated, no such segment). `GET /api/day1/clusters/{name}/network` (ADR-0039) |
| What day1 calls on segments-manager | nothing (only a link) | `GET /api/segments/by-segment?segment=<cidr>`, one segment per cluster page, cached per replica for `DAY1_CACHE_TTL_SECONDS`. No token; never a write |
| Chart | `segmentsManager.uiUrl` | also `segmentsManager.url`, `.sslVerify`, `.timeoutSeconds`. `uiUrl` may now be empty: the links then use `url` |

Without `segmentsManager.url` the card shows the file's VLAN and segment and
an EPG of "—", as an off feature. Nothing is written to GitLab, no
Secret changes, and the MCE grants are the same as 3.4's.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for 3.4.

## 3. Find segments-manager (read-only)

```bash
oc get svc -A | grep segments-manager       # its API Service: <sm-ns>/<sm-svc>, port <sm-port>
oc get route -A | grep segments-manager     # its UI, for uiUrl
```

From a day1 pod, check that it answers (any /24 a cluster file has in
`dhcp_values.network`):

```bash
kubectl -n <ns> exec deploy/wingman-day1 -- python -c \
  "import urllib.request as u; print(u.urlopen('http://<sm-svc>.<sm-ns>.svc:<sm-port>/api/segments/by-segment?segment=<a.b.c.0>/24', timeout=5).status)"
```

`200`, or `HTTP Error 404` (a segment it does not have), means day1 can reach it. A
timeout or a refused connection means it cannot: **STOP** and report. Do not
add a network policy to fix it.

## 4. Upgrade

Add the segments-manager values to step 7 of [3.3-to-3.4.md](3.3-to-3.4.md)'s
command, as `-f network-values.yaml`:

```yaml
segmentsManager:
  url: http://<sm-svc>.<sm-ns>.svc:<sm-port>
  uiUrl: https://<segments-manager UI host>   # keep 3.4's value; empty: url
```

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values -f network-values.yaml \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

## 5. Verify

Open a cluster whose file has `vlanId` and `dhcp_values.network`. The card
shows its VLAN, its Segment and an EPG. Or, with a session token as in
3.3-to-3.4's step 8:

```bash
curl -s -H "Authorization: Bearer $SESSION" \
  "https://<route host>/api/day1/clusters/<cluster>/network?site=<site>&mce=<mce>"
```

| What it shows | Means | Do |
|---|---|---|
| `epg` set, `problems` empty | segments-manager agrees with the file | Done |
| `problems` lists sentences | segments-manager disagrees with Git on this cluster | Report them: the file is right by definition, segments-manager's record needs a look |
| `ledger_error` set | day1 could not read segments-manager | Step 3 again with the URL from values |
| everything `null` but `vlan_id`/`segment` | `segmentsManager.url` is empty | Step 4's values were not applied |

## 6. Roll back and report

Roll back with `helm rollback <release> <previous revision> -n <ns>`; 3.4
ignores the new keys. Report: the tag deployed, step 3's status code, and
step 5's answer for one cluster (it holds no secret).
