# Upgrade: 3.3 → 3.4 (a cluster's nodes, by NodePool)

For an agent inside the disconnected environment. Follow the steps in order.
Every check says what to do when it fails, and **STOP** means: change
nothing more, finish the report (step 9) and hand it back.

Throughout, `<ns>`, `<release>`, `<registry>`, `<tag>` and `$CHART` mean what
they mean in [legacy-to-ecosystem.md](legacy-to-ecosystem.md); `<tag>` is
`3.4.0` or a later 3.4 release. On the MCE side:
- `<mce>` is an MCE's name, as a key of the tokens Secret, and `<domain>` is
  `clusterStatus.mceDomain`: the hub's API is `https://api.<mce>.<domain>:6443`.
- `<sa-ns>` and `<sa>` are the namespace and name of the service account
  whose token Wingman holds for that MCE (step 3 finds them).
- `<c>` is a cluster's `clusterName`: its file name without `.yaml` and, in
  production, without `ocp4-`. Its HostedCluster is `ocp4-<c>` in `hcp-<c>`,
  and its control-plane namespace is `hcp-<c>-ocp4-<c>`.

## 1. What changes

| Area | 3.3 | 3.4 |
|---|---|---|
| A cluster's page | live status: the HostedCluster and its NodePools | also a Nodes tab: each NodePool's nodes, what is missing and why, and which node an update is working on (`GET /api/day1/clusters/{name}/nodes`) |
| What day1 reads on each MCE hub | `hostedclusters`, `nodepools`, `infraenvs` | also `machines`, `machinesets`, `agentmachines` and `agents` (step 5). Read-only, never a Secret |
| server-scan (optional) | — | each node's server record and a link to it, and the servers server-scan places in the cluster that no Machine leads to: `serverScan.*` |
| Workflows orchestrator (optional) | — | an admin can start the platform's `uninstall-server-from-hc` workflow on one node and follow its run: `workflows.*`, which needs `serverScan.url` |
| segments-manager (optional) | — | the cluster page links to segments-manager's UI and to its search for the cluster's segment (JSON): `segmentsManager.uiUrl`. Only a link: day1 never calls it |
| Chart | — | the new keys `serverScan.*`, `workflows.*` and `segmentsManager.uiUrl`, off by default. `workflows.url` without `serverScan.url` fails the render |

No existing setting, Secret or value changes, and nothing is written to
GitLab. Without the new MCE reads, live status works as before; only the
Nodes tab fails, with a 502 that names what the hub denied.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, exactly as in
[legacy-to-ecosystem.md](legacy-to-ecosystem.md) step 2. Optionally, a
server-scan viewer token, if the team wants server records on the Nodes tab
and its server-scan has auth on.

## 3. Discover (read-only)

```bash
helm list -n <ns>                                    # the release and its chart
helm history <release> -n <ns>                       # the revision to roll back to
kubectl -n <ns> get deploy -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image
kubectl -n <ns> get configmap wingman-config -o jsonpath='{.data.CLUSTER_STATUS_ENABLED}{"\n"}{.data.MCE_API_DOMAIN}{"\n"}'
helm get values <release> -n <ns> --all -o yaml | grep -A4 '^clusterStatus:'   # enabled, mceDomain, sslVerify, tokensSecretName
helm version --short
```

Record the running version (each image's tag). **STOP** if it is not a 3.3
release: upgrade to 3.3 first ([3.2-to-3.3.md](3.2-to-3.3.md)).

If live status is off (`CLUSTER_STATUS_ENABLED` is `false`), the Nodes tab
will say so (501) and nothing reads the hubs: skip steps 4.3, 4.4 and 5, and
record it. Turning live status on is not part of this upgrade.

With live status on, list the MCEs that have a token. The tokens Secret is
`clusterStatus.tokensSecretName` (default `mce-sa-tokens`); its key `tokens`
is a YAML map of MCE name to token. Print the names only, never the tokens:

```bash
kubectl -n <ns> get secret mce-sa-tokens -o jsonpath='{.data.tokens}' | base64 -d \
  | sed -n 's/^\([^[:space:]#][^:]*\):.*/\1/p'
```

For each `<mce>`, find the service account behind its token, without
printing the token:

```bash
TOKEN=$(kubectl -n <ns> get secret mce-sa-tokens -o jsonpath='{.data.tokens}' | base64 -d \
  | sed -n 's/^<mce>:[[:space:]]*//p' | tr -d "\"'")
oc whoami --server=https://api.<mce>.<domain>:6443 --token="$TOKEN" --certificate-authority=<hub CA file>
unset TOKEN
```

It prints `system:serviceaccount:<sa-ns>:<sa>`. Use the TLS flag you use for
that hub (`--insecure-skip-tls-verify` only if `clusterStatus.sslVerify` is
`"false"`). Record `<mce>`, `<sa-ns>` and `<sa>` for each. If it prints a user
rather than a service account, the grant in step 5 binds that user instead
(`kind: User`); record it.

## 4. Check

1. **The version is 3.3** (step 3).
2. **Helm can bring in the new keys.** Upgrade with `--reset-then-reuse-values`
   (Helm 3.14 or later; step 7), or on an older Helm with the values-file
   form of step 7. Avoid `--reuse-values`: it renders 3.4's chart with only
   the values 3.3 had and ignores every new default in `values.yaml`. The
   chart supplies the defaults of `serverScan` and `workflows` itself, so it
   still renders, but nothing else new would be defaulted.
3. **You can grant on each hub.** For each `<mce>` from step 3, logged in to
   that hub:

   ```bash
   oc auth can-i create clusterroles.rbac.authorization.k8s.io          # yes
   oc auth can-i create clusterrolebindings.rbac.authorization.k8s.io   # yes
   oc get clusterrole,clusterrolebinding wingman-mce-reader            # NotFound, or the grant of step 5
   ```

   If you cannot create them, **STOP**: report which hub, and hand the YAML
   of step 5 to its administrators. If a `wingman-mce-reader` exists with
   other rules or another subject, **STOP**: do not overwrite it.
4. **The resources and namespaces are where Wingman reads them.** On each
   hub, for one cluster `<c>` it hosts:

   ```bash
   oc api-resources --api-group=cluster.x-k8s.io | grep -E '^machines |^machinesets '
   oc api-resources --api-group=capi-provider.agent-install.openshift.io | grep '^agentmachines '
   oc api-resources --api-group=agent-install.openshift.io | grep -E '^agents |^infraenvs '
   oc get machines.cluster.x-k8s.io -n hcp-<c>-ocp4-<c>
   oc get hostedcluster ocp4-<c> -n hcp-<c> -o jsonpath='{.spec.platform.agent.agentNamespace}{"\n"}'
   ```

   Each resource is listed, the Machines of `<c>` are there, and the last
   command prints the agent namespace (record it as `<agent-ns>`). If a
   resource is missing, the hub is not HyperShift on MCE with the Agent
   platform: **STOP**. If the Machines are in another namespace, **STOP** and
   report it: Wingman derives the control-plane namespace as
   `hcp-<c>-ocp4-<c>`.

## 5. Grant the new reads, on each MCE hub

Wingman needs `get` and `list` on these, through the token's service account:

| Resources | API group | Namespace |
|---|---|---|
| hostedclusters, nodepools | `hypershift.openshift.io` | `hcp-<c>` |
| machines, machinesets | `cluster.x-k8s.io` | `hcp-<c>-ocp4-<c>` |
| agentmachines | `capi-provider.agent-install.openshift.io` | `hcp-<c>-ocp4-<c>` |
| agents, infraenvs | `agent-install.openshift.io` | the HostedCluster's agent namespace |

A control-plane namespace is created per cluster, so the grant is one
ClusterRole and one ClusterRoleBinding per hub. It reads no Secrets.

First, on each hub, ask whether the account can already read them:

```bash
SA=system:serviceaccount:<sa-ns>:<sa>
oc auth can-i list machines.cluster.x-k8s.io -n hcp-<c>-ocp4-<c> --as=$SA
oc auth can-i list machinesets.cluster.x-k8s.io -n hcp-<c>-ocp4-<c> --as=$SA
oc auth can-i list agentmachines.capi-provider.agent-install.openshift.io -n hcp-<c>-ocp4-<c> --as=$SA
oc auth can-i list agents.agent-install.openshift.io -n <agent-ns> --as=$SA
```

If all four say `yes` (the account already has a wider role), skip the
apply for that hub and record it. Otherwise save this as
`wingman-mce-reader.yaml`, with the service account from step 3:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: wingman-mce-reader
rules:
  - apiGroups: [hypershift.openshift.io]
    resources: [hostedclusters, nodepools]
    verbs: [get, list]
  - apiGroups: [cluster.x-k8s.io]
    resources: [machines, machinesets]
    verbs: [get, list]
  - apiGroups: [capi-provider.agent-install.openshift.io]
    resources: [agentmachines]
    verbs: [get, list]
  - apiGroups: [agent-install.openshift.io]
    resources: [agents, infraenvs]
    verbs: [get, list]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: wingman-mce-reader
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: wingman-mce-reader
subjects:
  - kind: ServiceAccount
    name: <sa>
    namespace: <sa-ns>
```

Apply it, then ask again with the four `can-i` commands above:

```bash
oc apply -f wingman-mce-reader.yaml
```

Every answer must be `yes`. If one says `no` after the apply, **STOP**: report
the hub, the resource, and `oc get clusterrolebinding wingman-mce-reader -o yaml`
(it names no secret). Repeat for every MCE that has a token. The Wingman
deployment does not change for this step, and the grant works on 3.3 too, so
it can be done before the upgrade.

## 6. Optional: server-scan, the orchestrator and the segments-manager link

Skip this step unless the team wants them. All stay off without it, and
the Nodes tab still lists every node from the MCE.

1. **server-scan.** Find its API Service (`oc get svc -A | grep server-scan`)
   and its UI Route (`oc get route -A | grep server-scan`); if it runs on
   another cluster, its API is reached through its Route. If its auth is on,
   put a viewer token in a Secret in `<ns>`, never in values:

   ```bash
   oc create secret generic server-scan-viewer -n <ns> --from-literal=token=<viewer token>
   ```

   (`--from-file=token=<file>` keeps it out of the shell history.) Leave
   `tokenSecret.name` empty for a server-scan with auth off.
2. **The orchestrator** (`oc get svc -A | grep workflows-orchestrator-api`).
   It has no auth: with it on, Wingman's admins can start an uninstall,
   which removes a server from its cluster and cannot be undone. It needs
   `serverScan.url`; the chart refuses to render without it
   (`workflows.url needs serverScan.url`).
3. **The segments-manager link.** Its UI Route (`oc get route -A | grep segments-manager`).
   It is only a link the browser opens: day1 never calls segments-manager.

Write what applies as `nodes-values.yaml`:

```yaml
serverScan:
  url: http://server-scan-api.<server-scan ns>.svc:8000
  uiUrl: https://<server-scan UI host>      # where the node links point; empty: url
  sslVerify: "true"                         # "true", "false" or a CA bundle path
  tokenSecret:
    name: server-scan-viewer                # empty: no token
    key: token
workflows:
  url: http://workflows-orchestrator-api.<workflows ns>.svc:8080
  sslVerify: "true"
segmentsManager:
  uiUrl: https://<segments-manager UI host>
```

## 7. Upgrade

With Helm 3.14 or later (add `-f nodes-values.yaml` if you wrote it in step 6):

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

With an older Helm, pass the release's values as a file instead:

```bash
helm get values <release> -n <ns> -o yaml > current-values.yaml   # holds secrets: never print it, never hand it back
helm upgrade <release> $CHART -n <ns> -f current-values.yaml \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
rm current-values.yaml
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

Use the image value names your release's `$CHART/values.yaml` has, if they
differ from these.

## 8. Verify

1. **The nodes of a known cluster**, one with Machines on an MCE that has a
   token. Sign in to Wingman in the browser and copy the value of its
   `wingman-token` cookie (a session token; it expires with the session):

   ```bash
   SESSION=<the wingman-token cookie's value>
   curl -s -o nodes.json -w '%{http_code}\n' -H "Authorization: Bearer $SESSION" \
     "https://<route host>/api/day1/clusters/<cluster>/nodes?site=<site>&mce=<mce>"
   unset SESSION
   ```

   Add `--cacert <CA file>` if the Route's certificate is internal.
   `nodes.json` holds no secret. What the status means:

   | Status | Means | Do |
   |---|---|---|
   | `200` | `node_pools` lists the cluster's NodePools, each with its nodes | Compare with `oc get machines.cluster.x-k8s.io -n hcp-<c>-ocp4-<c>` on the hub: one node per Machine, plus a `missing` row for each the pool wants and does not have |
   | `502` | `code` is `DEPENDENCY_UNAVAILABLE`. A `detail` naming a 403 on a `/apis/...` path means the grant is missing there | Step 5 for that MCE and resource. Another detail means the hub did not answer: check it as for live status |
   | `501` | `code` is `FEATURE_DISABLED`: live status is off | Expected if step 3 found it off |
   | `404` | no such cluster | Check the name, site and MCE |
   | `401` | the session token is missing or expired | Sign in again and copy the cookie again |

   Or open the cluster's page in the browser: its Nodes tab shows the same.
2. **If you did step 6**, in the same answer: `server_scan_error` is `null`
   and the nodes have a `server` (a set `server_scan_error` means server-scan
   could not be read: its URL, token or CA; the nodes still list), and
   `uninstall.available` is `true` with `runs_error` `null` when the
   orchestrator is on.
3. **If you set `segmentsManager.uiUrl`**: open a cluster's page. Its
   **HostedCluster & network** card has a **Segments Manager** link to the UI,
   and **this cluster's segment (JSON)** lists its segment (none before
   allocate-segment has run). No link means the value did not reach day1:
   `oc get configmap wingman-config -n <ns> -o yaml | grep SEGMENTS_MANAGER`.
4. **Do not start an uninstall to test.** It removes the server from the
   cluster and the MCE, and cannot be undone.

## 9. Roll back and report

- **Roll back:** `helm rollback <release> <revision from step 3> -n <ns>`.
  Nothing was written to GitLab.
  - The RBAC grant is read-only and harmless to leave. To remove it, on each
    hub: `oc delete clusterrolebinding wingman-mce-reader` and
    `oc delete clusterrole wingman-mce-reader`. Remove it only where step 5
    created it.
  - 3.3 does not read the `server-scan-viewer` Secret; keep it or delete it.
  - An uninstall started from 3.4 keeps running in the orchestrator; 3.3
    does not show it.
- **Report:** the versions before and after; whether live status is on; per
  MCE, the service account, whether step 5 applied the grant or found it
  already there, and each `can-i` answer; whether step 6 configured
  server-scan, the orchestrator and the segments-manager link; and step 8's
  status for each cluster you checked, with `server_scan_error` and
  `runs_error`. Never a token or `current-values.yaml`.
