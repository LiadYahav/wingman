# Upgrade: 3.39 → 3.40 and later (scale NodePools through update-nodepool, optional)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 6) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md). `<tag>` is `3.40.0` or any later release:
3.41 moved Scale onto each NodePool's card, 3.42 asks before every
scale, 3.45.1 sets one NodePool a run (the workflow no longer takes a
hardware kind total), and 3.46 lets a scale-down pick its servers. This
guide covers all of them.

## 1. What changes

| Area | 3.39 | 3.40 and later |
|---|---|---|
| A NodePool's replicas | Changed by an edit (a merge request), or by a flavor's sync or rollout | The same by default. With `day1.scaleNodepools.enabled: true`, an admin scales on the cluster's Nodes tab: a − N + on each NodePool (that NodePool, exact; before 3.45.1 also a hardware type's total, spread by the workflow). Wingman starts the platform's `update-nodepool` workflow and shows its run (ADR-0062) |
| Edits while it is on | — | An edit that changes an existing NodePool's `replicas` is refused, and points to Scale. A flavor's sync or rollout leaves drifted replicas out of its merge request and offers "Restore to N", which starts the workflow. A NodePool a flavor locks is never scaled, only restored |
| Before a scale | — | A short confirmation (3.42+). On a scale-down it says which nodes leave, by the NodePool's `redbull.io/scale-down-policy`, read from the day1 file |
| Chart | — | `day1.scaleNodepools.enabled` (`false` by default). `true` needs `workflows.url`; the chart refuses to render without it |
| Metrics | — | `workflows` gains the operation `start_update_nodepool` (`docs/ops/metrics.md`) |

With the default, nothing changes and there is nothing to do but the image
tags. The rest of this guide is for turning Scale on.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for any
release. Nothing else for Wingman itself. The platform side (step 3) must
already be in place.

## 3. Check before turning it on (read-only)

1. **The orchestrator has the workflow.** From a day1 pod:

   ```bash
   kubectl -n <ns> exec deploy/wingman-day1 -- python -c \
     "import urllib.request as u, json; d = json.load(u.urlopen('<workflows.url>/openapi.json', timeout=5)); print('/workflows/server-lifecycle/update-nodepool' in d['paths'])"
   ```

   `True`: go on. `False`, or no answer: **STOP**. The orchestrator is older
   than the workflow, or day1 can't reach it. Don't add a network policy to
   fix it.
2. **Every MCE's server-lifecycle worker can run it.** The workflow runs
   every call on the MCE's own worker. On each MCE that runs hosted
   clusters, the `server-lifecycle-worker` release must have:
   - `day1.repoUrl` set to **the same day1 repo Wingman reads**, and its
     push token (`DAY1_GIT_TOKEN`, from the credentials Secret or
     `day1.tokenSecret`);
   - `rbac.hostedClusters: true` (Machines, NodePools, the hosted cluster's
     admin kubeconfig) and `argo.namespace` set to where the hosted clusters'
     Argo CD Applications live;
   - network access to the day1 Git server.

   Without these, a scale fails at its first call, with nothing written
   (`Day1NotConfiguredError`, or a call no worker picks up). If one MCE is
   not ready, **STOP** and report which.
3. **The team agrees who writes replicas.** While it is on, a merge request
   no longer changes an existing NodePool's replicas, and the workflow
   commits them straight to day1 `main` and has Argo CD apply them. Record in
   the report that the team chose this.
4. **The scale-down policy (optional).** On a scale-down, a NodePool with a
   `redbull.io/scale-down-policy` (`fewest-pods`, `least-requested`,
   `least-utilized`) has the leaving nodes chosen by it; without one, CAPI
   picks at random. Wingman reads it from the nodepool entry's
   `annotations` in the day1 file. For it to reach the NodePool:
   - the hostedclusters-setup chart must render a nodepool entry's
     `annotations` onto the NodePool (team-redbull/helm-charts-hostedclusters-setup,
     PR #4). Check your copy's `templates/nodepool.yaml` for it. Without it,
     the annotation in the file does nothing, and the policy can only be set
     on the NodePool itself (`oc annotate nodepool <name> -n hcp-<cluster>
     redbull.io/scale-down-policy=fewest-pods`), which Wingman can't show;
   - `least-utilized` needs the metrics API on the hosted cluster, or the
     run fails (`NodeMetricsUnavailableError`).

   None of this blocks turning Scale on: without a policy, scale-downs are
   at random, as they are today.
5. **Picking the servers a scale-down removes (3.46+, optional).** The
   confirmation lists the NodePool's servers to tick exactly the ones that
   leave; none ticked, the policy (or CAPI) picks as before. It needs:
   - live status (`clusterStatus`), since the list is the Nodes tab's read
     of the MCE; without it the confirmation says there is nothing to pick;
   - an orchestrator and every MCE's `server-lifecycle-worker` from the
     workflows release that has update-nodepool's `server_names` (branch
     `feat/update-nodepool`, 2026-11-18 or later). With an older orchestrator
     a named scale-down is refused (422, nothing started); with an older
     worker the run waits, RUNNING, or fails with
     `ScaleDownServersInvalidError`, nothing marked or written;
   - the workflow documents it for OpenShift 4.19 and later; on 4.18 it
     refuses a pick that CAPI could override (an unhealthy machine left
     unpicked).

   Record in the report which MCEs' workers are new enough. Nothing else to
   set in Wingman.

## 4. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag> \
  --set day1.scaleNodepools.enabled=true   # leave this line out to keep Scale off
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

The render fails with "day1.scaleNodepools.enabled needs workflows.url"
when the release has no `workflows.url`: set it as in 3.3-to-3.4's step 6,
or leave Scale off.

## 5. Verify

With a session token as in 3.3-to-3.4's step 8, for any cluster:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $SESSION" \
  "https://<route host>/api/day1/clusters/<cluster>/scale"
```

`200` means Scale is on; `501` means it is off. Don't scale a cluster to test
it: a scale is a real commit to day1 `main`, applied by Argo CD. The cluster's
Nodes tab shows the − N + controls to admins.

## 6. Roll back and report

Roll back Scale alone with `--set day1.scaleNodepools.enabled=false`. Edits
then change replicas again, as in 3.39. Or roll back the release with
`helm rollback <release> <previous revision> -n <ns>`; 3.39 ignores the new
key. Report: the tag deployed, whether Scale is on, step 3's answers per MCE,
and step 5's answer.
