# Upgrade: 3.46 → 3.47 (a nodepool may draw from several InfraEnvs, off by default)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 8) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.47.0` or a later 3.47 release.

## 1. What changes

| Area | 3.46 | 3.47 |
|---|---|---|
| A nodepool | Draws Agents from one InfraEnv, `infraEnvName` | With `day1.multiInfraEnvNodepools.enabled`, it may also draw from others, listed in `additionalInfraEnvNames` (ADR-0064). `infraEnvName` stays and still names the NodePool |
| The create form, the flavor editor, Edit cluster | One InfraEnv per nodepool | With the setting on: the nodepool's own InfraEnv, then **Also draws from** |
| The cluster file | — | `additionalInfraEnvNames: [..]` under a nodepool, written only when it draws from more than one. Without it, every file is written exactly as before |
| Refused | — | An edit that makes another InfraEnv first, which would replace the NodePool; a change of the InfraEnvs of an `upgradeType: Replace` NodePool; with the setting off, any edit of `additionalInfraEnvNames`; a template that does not write the input |
| Placement and Inventory Management | — | A nodepool's free servers are counted over all its InfraEnvs, none twice |
| Chart | — | `day1.multiInfraEnvNodepools.enabled` (`false` by default) |
| Secrets, grants, metrics | — | Nothing new |

**With the setting off, nothing changes**: the upgrade is the image tags
(step 6). Turning it on needs two things first, in this order:

1. The hostedclusters-setup chart that builds the clusters renders
   `additionalInfraEnvNames` (step 4). A chart that does not ignores the
   key and gives the NodePool its first InfraEnv alone, without a word.
2. The specs project's `cluster-template.j2` writes it (step 5).

The team decides whether to turn it on now or later. Record which.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for any
release. The reference template is in that repository:
`dev/gitlab-fixtures/wingman/cluster-specs/cluster-template.j2`.

To turn the feature on, also bring the hostedclusters-setup chart change.
Its tests (`tests/test_nodepool_infra_envs.py`) come with it.

## 3. Discover (read-only)

1. **The chart.** In the chart repo that builds the HostedClusters, open
   `templates/nodepool.yaml`. Search it for `additionalInfraEnvNames`.
   - Found: the chart already renders it. Step 4 is its check only.
   - Not found: step 4 is needed before the setting is turned on.
2. **The template.** In the specs project (`gitlab.specsProjectId`), open
   `cluster-template.j2` on the default branch. Search it for
   `additional_infra_envs` and `additionalInfraEnvNames`.
   - Neither: step 5 adds the lines.
   - Both: done. Step 5 is its check only.
   - Only `additionalInfraEnvNames`: the template writes the key itself.
     **STOP** and report the lines.
3. Note the line that writes `infraEnvName:` inside the nodepool loop
   (`{% for np in nodepools %}`) and its indentation. Step 5's lines go
   directly below it.
4. **herzi.** herzi counts a NodePool's demand only from its one
   `infraenvs.agent-install.openshift.io` label. It orders no servers for
   a NodePool that draws from several InfraEnvs. Report whether the team
   relies on herzi for the MCEs where this would be used.

## 4. The chart (only to turn the feature on)

Apply the chart change through the chart repo's own review. Then, before
merging, render one nodepool with two InfraEnvs:

```bash
helm template t <chart-dir> -f <a cluster file with additionalInfraEnvNames> \
  --set-string clusterName=<name> --show-only templates/nodepool.yaml
```

Expect, for that nodepool:

```yaml
      agentLabelSelector:
        matchExpressions:
        - key: infraenvs.agent-install.openshift.io
          operator: In
          values:
          - "<first>"
          - "<other>"
```

Its name is still `<clusterName>-<infraEnvName>`. Every other nodepool, and
every existing cluster file, renders exactly as before: run the chart's own
tests. Anything else: **STOP**.

## 5. The specs project's template (only to turn the feature on, through an MR)

Open an MR on the specs project that adds exactly these lines to
`cluster-template.j2`, directly below the `infraEnvName:` line of step 3.3.
Indent `additionalInfraEnvNames:` like the keys below `infraEnvName:` in
that template (four spaces in the reference); the template tags start at
column 0.

```jinja
{% if np.additional_infra_envs | default([]) %}
    additionalInfraEnvNames: {{ np.additional_infra_envs | tojson }}
{% endif %}
```

- `| default([])` keeps the input optional: a nodepool without it renders
  as before.
- `| tojson` writes `["a", "b"]`, each name quoted.
- Day1 checks that every rendered file holds exactly the InfraEnvs chosen,
  and none where none were chosen. A flavor that gives them is refused
  while the template does not read them.

A person with rights on the specs project merges it. Record the MR.

## 6. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
  # --set day1.multiInfraEnvNodepools.enabled=true   only once steps 4 and 5 are done
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

## 7. Verify

1. Clusters and Flavors load as before. A cluster's page shows each
   nodepool's InfraEnv as before.
2. Setting off: `GET /api/day1/specs/template/schema` (with a session
   token, as in 3.3-to-3.4's step 8) does not list `additional_infra_envs`.
3. Setting on: it does. On the create form, pick any flavor and an MCE, add
   a second InfraEnv to the first nodepool under **Also draws from**, and
   press **Preview** (it commits nothing). The file shows
   `additionalInfraEnvNames:` under that nodepool only. Leave the form
   without creating.

## 8. Roll back and report

Roll back with `helm rollback <release> <previous revision> -n <ns>`, or turn
the setting off alone with `--set day1.multiInfraEnvNodepools.enabled=false`.
A file that already has `additionalInfraEnvNames` keeps it either way:
- 3.46 ignores it, and it stays in the file;
- 3.47 with the setting off keeps it as it is.

Revert step 5's MR only when no flavor gives the input.

Report:
- the tag deployed;
- whether the setting is on;
- step 3's answers, and the herzi question;
- the chart change and step 5's MR, if done;
- step 7's results.
