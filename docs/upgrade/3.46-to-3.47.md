# Upgrade: 3.46 → 3.47 (a nodepool may draw from several InfraEnvs, off by default)

> **2026-11-23: the feature is parked** (ADR-0064's amendment). The team runs
> no NodePool that draws from several InfraEnvs for now. Do the upgrade with
> the setting off (step 6's image tags) and skip what turns it on: don't
> apply the chart change for `additionalInfraEnvNames`, don't add step 5's
> template lines, and keep `day1.multiInfraEnvNodepools.enabled` false. The
> chart patches of steps 2 to 4 and 9 are now two, `annotations` and
> `excludeAgentLabels`: apply and check them as
> [patches/hostedclusters-setup/README.md](patches/hostedclusters-setup/README.md)
> says, not as step 4 below.

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 8) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.47.0` or a later 3.47 release.

## 1. What changes

| Area | 3.46 | 3.47 |
|---|---|---|
| A nodepool | Draws Agents from one InfraEnv, `infraEnvName` | With `day1.multiInfraEnvNodepools.enabled`, it may also draw from others, listed in `additionalInfraEnvNames` (ADR-0064). `infraEnvName` stays and still names the NodePool |
| The create form, the flavor editor, Edit cluster | One InfraEnv per nodepool | With the setting on: the nodepool's own InfraEnv, then **Also draws from** |
| The cluster file | — | `additionalInfraEnvNames: [..]` under a nodepool, written only when it draws from more than one. Without it, every file is written exactly as before |
| Refused | — | An edit that makes another InfraEnv first, which would replace the NodePool; a change of the InfraEnvs of an `upgradeType: Replace` NodePool; with the setting off, any edit of `additionalInfraEnvNames`; a template that does not write the input |
| Placement and Inventory Management | — | A nodepool's free servers are counted over all its InfraEnvs, none twice |
| Chart | — | `day1.multiInfraEnvNodepools.enabled` (`false` by default) |
| The hostedclusters-setup chart | — | Three patches in this repository, [`patches/hostedclusters-setup/`](patches/hostedclusters-setup/): a nodepool's `annotations`, `additionalInfraEnvNames`, and `excludeAgentLabels` (step 4, step 9). Each leaves every existing cluster file's render byte for byte as it was |
| Secrets, grants, metrics | — | Nothing new |

**With the setting off, nothing changes**: the upgrade is the image tags
(step 6). Turning it on needs three things, in this order:

1. **The chart.** The hostedclusters-setup chart that builds the clusters
   renders `additionalInfraEnvNames` (step 4). A chart that does not
   ignores the key and gives the NodePool its first InfraEnv alone, without
   a word.
2. **The template.** The specs project's `cluster-template.j2` writes it
   (step 5).
3. **The setting.** `day1.multiInfraEnvNodepools.enabled=true` (step 6).

The team decides whether to turn it on now or later. Record which. The chart
patches may go in now either way: they change no existing NodePool.

## 4. The chart (only to turn the feature on, through an MR)

The chart goes first. Make the change on a branch of the chart repo (the
copy that the ApplicationSet of step 3.1 reads), check that no existing
cluster renders differently, and merge through the chart repo's own review.
The air-gapped chart takes the change from its own separate package (follow
that package's instructions for 4.2); 4.1 and 4.3 apply as written.

### 4.1 Render every cluster file before the change (read-only)

In a clone of the day1 values repo at `main`, render every cluster file with
the chart as it is, the way the ApplicationSet does: the four value files
that exist, in its order, and its parameters. With production's
`clusterName` only (the file's own `clusterName`, else its name without
`.yaml` and the `ocp4-` prefix):

```bash
render_all() {  # <chart dir> <output dir> [more helm flags]; from the day1 repo's root
  local chart=$1 out=$2 f site mce stem name layer
  shift 2
  mkdir -p "$out"
  for f in sites/*/mces/*/hostedClusters/*; do
    site=$(echo "$f" | cut -d/ -f2); mce=$(echo "$f" | cut -d/ -f4)
    stem=$(basename "$f" .yaml)
    name=$(sed -n 's/^clusterName: *//p' "$f" | tr -d "\"' ")
    [ -n "$name" ] || name=${stem#ocp4-}
    files=()
    for layer in sites/configValues.yaml "sites/$site/values.yaml" \
        "sites/$site/mces/$mce/values.yaml" "$f"; do
      [ -f "$layer" ] && files+=(-f "$layer")
    done
    helm template "$stem" "$chart" "${files[@]}" --set-string "clusterName=$name" "$@" \
      >"$out/$site.$mce.$stem.yaml" 2>"$out/$site.$mce.$stem.err"
    echo "exit $?" >>"$out/$site.$mce.$stem.err"
  done
  ls "$out"/*.yaml | wc -l
}
git -C <chart repo> checkout main
render_all <chart repo> /tmp/render-before
```

If the ApplicationSet passes more parameters (the connected copy also passes
`site` and `mce`), add them to `--set-string`. Record the number of files.
Each `.err` file should end in `exit 0`; one that does not fails today too:
record it, it is not this change's.

### 4.2 Apply the patches (a chart that is the public port, or close to it)

```bash
cd <chart repo>
git checkout -b feat/nodepool-selectors main
git am -3 <patches>/0001-*.patch <patches>/0002-*.patch <patches>/0003-*.patch
```

Skip a patch whose key step 3.1 found (`git am --skip` when it stops on it,
or leave its file out of the command). The patches are made on the public
GitHub port, so on another copy `git am` may stop on a hunk that does not
match:

- `git am --show-current-patch=diff` shows the patch it stopped on.
- **A hunk of `README.md` or `tests/`** where the copy has no such file or
  other text: write the same lines where they fit, or leave them out. The
  tests need the port's `tests/fixtures/hostedcluster/`; a copy without that
  folder leaves the test file out (`git rm --cached` it) and relies on 4.3.
- **A hunk of `templates/nodepool.yaml`:** apply it by hand. Each is a few
  lines and the patch's message says what it does.
- Then `git add` the files and `git am --continue`.

### 4.3 Check, before merging

1. **Nothing existing changes.** Render again with the branch and compare:

   ```bash
   git -C <chart repo> checkout feat/nodepool-selectors
   render_all <chart repo> /tmp/render-after
   diff -r /tmp/render-before /tmp/render-after && echo IDENTICAL
   ```

   Expect `IDENTICAL` and the same number of files: every cluster file,
   byte for byte. Anything else: **STOP**, and report the files that differ.
2. **The chart's own tests**, where the copy has them: `pytest -q` and
   `helm lint .`.
3. **The new shapes.** Copy one cluster file outside the day1 repo (never
   commit it: a file on `main` creates a cluster), give its first nodepool
   `additionalInfraEnvNames: [<another InfraEnv>]`, its second
   `annotations: {redbull.io/scale-down-policy: fewest-pods}` and its third
   `excludeAgentLabels: [example.com/used]`, and render it as in 4.1
   with `--show-only templates/nodepool.yaml`. Expect:

   ```yaml
   # the first: one In requirement, its own InfraEnv first; no matchLabels; the same name
         agentLabelSelector:
           matchExpressions:
           - key: infraenvs.agent-install.openshift.io
             operator: In
             values:
             - "<its InfraEnv>"
             - "<another InfraEnv>"
   # the second: the annotation after the chart's own sync-wave
     annotations:
       argocd.argoproj.io/sync-wave: "4"
       redbull.io/scale-down-policy: fewest-pods
   # the third: its InfraEnv label as before, then the In requirement and the label kept out
         agentLabelSelector:
           matchLabels:
             infraenvs.agent-install.openshift.io: <its InfraEnv>
           matchExpressions:
           - key: infraenvs.agent-install.openshift.io
             operator: In
             values:
             - "<its InfraEnv>"
           - key: "example.com/used"
             operator: DoesNotExist
   ```

   Every NodePool keeps its name (`<clusterName>-<infraEnvName>`, or its
   `name`). Anything else: **STOP**.

Then the chart repo's review merges the MR. Record it. Since every render is
the same, the hosted-cluster Applications show no change after Argo CD reads
the new chart: check that they stay Synced and Healthy.

## 9. Excluded Agent labels and nodepool annotations (optional, after the upgrade)

Two keys patches 0001 and 0003 add, which this upgrade does not use:

- **`nodepool[].annotations`** (0001) reach the NodePool as written
  (`toYaml`), after the chart's own `argocd.argoproj.io/sync-wave`. Values
  must be strings. The chart does not refuse an entry that sets the
  sync-wave itself (the NodePool would get it twice); Wingman's edits do.
  Scale's scale-down policy is one: `redbull.io/scale-down-policy`
  (`fewest-pods`, `least-requested`, `least-utilized`),
  [3.48-to-3.49.md](3.48-to-3.49.md) steps 4 and 5. An annotation changes no
  node.
- **`nodepool[].excludeAgentLabels`** (0003): label keys an Agent must not
  carry for the NodePool to take it. The NodePool's `agentLabelSelector`
  gains `matchExpressions`: the InfraEnvs' `In` requirement, then
  `{key: <key>, operator: DoesNotExist}` for each, beside `matchLabels` when
  the nodepool draws from one InfraEnv. Unset or empty, the selector is
  exactly what it was. The use is herzi's collector of used Agents: herzi
  labels every Agent installed in a cluster as used (an uninstall or a
  scale-down does not return a used Agent to the inventory cleanly) and
  deletes a free Agent that carries the label. Every NodePool excluding that
  label keeps a freed used Agent from being bound again before herzi deletes
  it. The label's name is herzi's to choose and not final yet.

**A changed selector** touches no running node on an `upgradeType:
InPlace` NodePool (the default): the Agent provider reads the selector only
when a new Machine claims an Agent. On a `Replace` NodePool, the same change
replaces every node, one by one. And herzi on its `main` reports a NodePool
with `matchExpressions` beside its InfraEnv label as a problem of that
InfraEnv's pool, which then orders no servers for any cluster: add the
exclusion only with the herzi release that labels used Agents and accepts
it.

The key is written per nodepool, in each cluster file (the approved chart
change has no chart-wide list), one merge request per cluster: each cluster
changes only when its own MR merges, reviewed and synced on its own, a small
blast radius. Wingman does this from its setting `DAY1_EXCLUDED_AGENT_LABELS`
for the clusters it creates, and opens one cluster's MR on request; it never
adds the key to an existing `Replace` NodePool
([3.48-to-3.49.md](3.48-to-3.49.md) step 9, ADR-0065).
