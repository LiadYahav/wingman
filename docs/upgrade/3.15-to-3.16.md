# Upgrade: 3.15 → 3.16 (upgrades through the upgrade-cluster workflow, optional)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 6) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.16.0` or a later 3.16 release.

## 1. What changes

| Area | 3.15 | 3.16 |
|---|---|---|
| A cluster's version | Edited in its file (`mastertag`, `workertag`) through a modify MR | The same by default. With `day1.upgrades.enabled: true`, an admin's **Upgrade** on the cluster page starts the platform's `upgrade-cluster` workflow toward a target the workflow offers. The run plans and checks, waits for an approval with nothing committed, then commits each step to day1 `main` itself. The cluster page shows the run and its decisions (ADR-0055) |
| Edits while it is on | — | A modify or a review edit that changes `mastertag` or a `workertag`, or adds `pausedUntil`, is refused: "Versions change through Upgrade on the cluster page". Removing `pausedUntil` (after an aborted upgrade) and a create's starting version stay editable |
| Chart | — | `day1.upgrades.enabled` (`false`), `workflows.targetsTimeoutSeconds` (`65`). On needs `workflows.url`: the chart refuses to render without it. On, the Route gets `haproxy.router.openshift.io/timeout: 130s`, and nginx gives `/api/day1/clusters/<name>/upgrade-targets` a 130 s read timeout: the targets read can take a minute |
| Metrics | — | `workflows` gains `upgrade_targets`, `start_upgrade`, `decide_upgrade` (`docs/ops/metrics.md`) |

With the default, nothing changes and there is nothing to do but the image
tags. The rest of this guide is for turning upgrades on.

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for 3.15.

## 3. Check before turning it on (read-only)

1. **The orchestrator has the workflow.** From a day1 pod:

   ```bash
   kubectl -n <ns> exec deploy/wingman-day1 -- python -c \
     "import urllib.request as u, json; d = json.load(u.urlopen('<workflows.url>/openapi.json', timeout=5)); print('/workflows/cluster-upgrade/upgrade-targets' in d['paths'])"
   ```

   `True`: go on. `False`, or no answer: **STOP**. The orchestrator is older
   than the workflow, or day1 can't reach it. Don't add a network policy to
   fix it.
2. **The workflow reads the same day1 repo as Wingman.** The upgrade's
   limbs read and write the day1 repo they are configured with; Wingman reads
   `gitlab.day1ProjectId` on `gitlab.url`. Ask the platform team which repo
   and project the upgrade-gitops limb uses, and compare. Different (Wingman
   on a copy of day1, a test GitLab): **STOP**. The targets would answer 404,
   or a run would upgrade the clusters of the other repo.
3. **The team agrees.** The workflow commits to day1 `main` without a merge
   request (its approval is the run's `approve`), and it is "not in
   production yet" on its own docs page
   (`docs/notes/2026-11-13-upgrade-cluster-workflow-api.md`, open questions
   1 and 2). Record in the report that the team chose to turn it on.

## 4. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag> \
  --set day1.upgrades.enabled=true          # leave this line out to keep upgrades off
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

The render fails with "day1.upgrades.enabled needs workflows.url" when the
release has no `workflows.url`: set it as in 3.3-to-3.4's step 6, or leave
upgrades off.

## 5. Verify

With a session token as in 3.3-to-3.4's step 8, and any cluster's file stem:

```bash
curl -s -o run.json -w '%{http_code}\n' -H "Authorization: Bearer $SESSION" \
  "https://<route host>/api/day1/clusters/<cluster>/upgrade-run"
```

| Status | Means |
|---|---|
| `404` | On, and the cluster has no upgrade run: as expected |
| `200` | On; `run.json` is the cluster's newest run |
| `501` | Off: the setting did not reach day1 (check `helm get values <release> -n <ns>`) |
| `502` | On, but the orchestrator did not answer: check `workflows.url` from a day1 pod |

Don't start an upgrade to test it: a start plans a real upgrade (nothing is
committed before its approval, and an Abort then ends it). Opening the
cluster page's **Upgrade** dialog only reads the targets.

## 6. Roll back and report

Turn upgrades off alone with `--set day1.upgrades.enabled=false` (an open
run keeps going in the orchestrator; Wingman stops showing it), or roll the
release back with `helm rollback <release> <previous revision> -n <ns>`;
3.15 ignores the new keys. Report: the tag deployed, whether upgrades are on,
step 3's answers and step 5's status.
