# Upgrade: 3.48 → 3.49 (a NodePool's scale-down policy for one run, optional)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 6) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.49.0` or a later 3.49 release.

## 1. What changes

| Area | 3.48 | 3.49 |
|---|---|---|
| Scale's scale-down confirmation (only with `day1.scaleNodepools.enabled`) | The NodePool's own `redbull.io/scale-down-policy` picks the servers that leave, or the admin ticks them | One choice of which servers leave: **the NodePool's own policy** (the default; without one CAPI picks at random), **another policy for this run**, or **pick the servers**. Exactly one is sent (ADR-0062's last 2026-11-18 amendment) |
| The run on the Nodes tab | The NodePool before and after, the servers chosen | Also which way its servers were chosen: by name, by its own policy, by this run's policy, or at random |
| Refused before anything is sent | A wrong count of servers, servers named on a scale-up | Also: a policy that is not `fewest-pods`, `least-requested` or `least-utilized`; a policy and servers at once; a policy on a scale-up or no change |
| Chart, Secrets, grants, metrics | — | Nothing new |

With Scale off (the default), nothing changes: the upgrade is the image
tags (step 4).

## 2. What to bring in from the connected side

The three images of `<tag>` and the repository at `v<tag>`, as for any
release.

For **another policy for this run**, the orchestrator and every MCE's
`server-lifecycle-worker` must come from the workflows release whose
update-nodepool takes `scale_down_policy` (branch `feat/update-nodepool`,
2026-11-18 or later: the same release that takes `server_names`, which
[3.39-to-3.40.md](3.39-to-3.40.md) step 3.5 already asks for). Without it
only that choice fails, and safely: the orchestrator refuses the field (422)
and nothing starts.

## 3. Check (read-only)

1. **Does the orchestrator take the override?** From a day1 pod (skip it
   when Scale is off):

   ```bash
   kubectl -n <ns> exec deploy/wingman-day1 -- python -c \
     "import urllib.request as u, json; d = json.load(u.urlopen('<workflows.url>/openapi.json', timeout=5)); print('scale_down_policy' in d['components']['schemas']['UpdateNodePoolRequest']['properties'])"
   ```

   - `True`: the override works.
   - `False`, or a `KeyError`: the orchestrator is older. The upgrade can go
     on; tell the admins that **another policy for this run** is refused
     until it is upgraded. Record which.
2. **`least-utilized` needs metrics.** It ranks a NodePool's nodes by their
   live CPU and memory use, from the hosted cluster's metrics API
   (`metrics.k8s.io`). On a hosted cluster without it the run fails with
   `NodeMetricsUnavailableError`, with nothing marked or written. Record
   whether the hosted clusters serve it; the others need nothing.

## 4. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

## 5. Verify

1. Clusters and Flavors load as before.
2. With Scale on: on a cluster's Nodes tab, lower a NodePool's stepper by
   one and press **Scale down**. The confirmation offers **Which servers
   leave**, its policy named. Press **Cancel**: nothing is sent. Don't scale
   a cluster to test it: a scale is a real commit to day1 `main`.

## 6. Roll back and report

Roll back with `helm rollback <release> <previous revision> -n <ns>`.
Nothing is stored by this release: a run started with a policy finishes as
it began.

Report:
- the tag deployed;
- step 3's answers;
- step 5's results.
