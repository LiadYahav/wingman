# Upgrade: 3.48 → 3.49 (a NodePool's scale-down policy: declared at create, chosen per run; optional)

For an agent inside the disconnected environment. Follow the steps in order.
**STOP** means: change nothing more, finish the report (step 8) and hand it
back.

`<ns>`, `<release>`, `<tag>` and `$CHART` mean what they mean in
[3.3-to-3.4.md](3.3-to-3.4.md); `<tag>` is `3.49.0` or a later 3.49 release.

## 1. What changes

A NodePool's scale-down policy says which servers leave when it scales
down: `fewest-pods` (the fewest workload pods), `least-requested` (the
lowest requested CPU or memory share) or `least-utilized` (the lowest live
use, from the hosted cluster's metrics API). Without one, CAPI picks at
random. The platform's `update-nodepool` workflow reads it from the
NodePool's `redbull.io/scale-down-policy` annotation (ADR-0062's last
2026-11-18 amendment).

| Area | 3.48 | 3.49 |
|---|---|---|
| The create form, the flavor editor | — | Each nodepool has a **Scale-down policy**: the platform default (writes nothing), or one of the three. A flavor may preset it or lock it. Offered only once the specs project's template reads it (step 5) |
| The cluster file | — | `annotations: {redbull.io/scale-down-policy: <policy>}` under a nodepool, written only when one is chosen. Without one, every file is written exactly as before |
| Edit cluster, drift, a flavor's merge requests | — | An edit may set a nodepool's policy to one of the three; drift and a flavor's per-cluster merge request write a locked one. Every edit keeps the annotation as it is. Changing it rolls no node |
| Scale's scale-down confirmation (only with `day1.scaleNodepools.enabled`) | The NodePool's own policy picks the servers that leave, or the admin ticks them | One choice of which servers leave: **the NodePool's own policy** (the default), **another policy for this run**, or **pick the servers**. Exactly one is sent |
| The run on the Nodes tab | The NodePool before and after, the servers chosen | Also which way its servers were chosen |
| Refused | — | A policy other than the three; a flavor or a create that gives a policy while the template does not render it; a lock to no policy; for a run, a policy and servers at once, or a policy on a scale-up |
| Chart, Secrets, grants, metrics | — | Nothing new in Wingman's chart |

**Nothing changes until someone chooses a policy**: the upgrade is the
image tags (step 6). A policy in the file reaches the NodePool only through
two changes outside Wingman, in this order:

1. The hostedclusters-setup chart that builds the clusters renders a
   nodepool entry's `annotations` onto its NodePool (step 4). A chart that
   does not ignores the key, without a word: the policy stays in the file,
   and update-nodepool never sees it.
2. The specs project's `cluster-template.j2` writes the input (step 5).
   Until then the form does not offer it, and a flavor or a create that
   gives it is refused with a message naming this guide.

A policy for **one run** (Scale) needs neither: it needs the workflows
release of step 2.

The team decides whether to do steps 4 and 5 now or later. Record which.

## 3. Discover (read-only)

1. **The chart.** In the chart repo that builds the HostedClusters, open
   `templates/nodepool.yaml`. Look in the NodePool's `metadata.annotations`
   for the entry's own map, read from the nodepool entry (`.annotations`),
   after the chart's `argocd.argoproj.io/sync-wave`.
   - Found: the chart already renders it. Step 4 is its check only.
   - Not found: step 4 is needed before anyone chooses a policy.
2. **The template.** In the specs project (`gitlab.specsProjectId`), open
   `cluster-template.j2` on the default branch. Search it for
   `scale_down_policy` and `annotations:`.
   - Neither: step 5 adds the lines.
   - Both, inside the nodepool loop: done. Step 5 is its check only.
   - `annotations:` alone, inside the nodepool loop: the template writes
     annotations of its own. **STOP** and report the lines: step 5's block
     would write the key twice, and day1 refuses such a file.
3. Note the `labels:` block inside the nodepool loop
   (`{% for np in nodepools %}`) and its last line
   (`allowDeletion: false` in the reference). Step 5's lines go directly
   below it.
4. **The orchestrator** (only with Scale on). From a day1 pod:

   ```bash
   kubectl -n <ns> exec deploy/wingman-day1 -- python -c \
     "import urllib.request as u, json; d = json.load(u.urlopen('<workflows.url>/openapi.json', timeout=5)); print('scale_down_policy' in d['components']['schemas']['UpdateNodePoolRequest']['properties'])"
   ```

   - `True`: a policy for one run works.
   - `False`, or a `KeyError`: the orchestrator is older. Go on; tell the
     admins that **another policy for this run** is refused until it is
     upgraded. Record which.
5. **`least-utilized` needs metrics.** It ranks a NodePool's nodes by their
   live use, from the hosted cluster's `metrics.k8s.io`. On a hosted cluster
   without it, a scale-down by that policy fails
   (`NodeMetricsUnavailableError`), nothing marked or written. Record whether
   the hosted clusters serve it.

## 4. The chart (only to declare policies in the file)

The hostedclusters-setup chart must render a nodepool entry's `annotations`
map onto its NodePool. In `templates/nodepool.yaml`, the NodePool's
`metadata.annotations` gains the entry's map, as written, after the chart's
own sync-wave:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "4"
    {{- with .annotations }}
    {{- toYaml . | nindent 4 }}
    {{- end }}
```

Make the change through the chart repo's own review. The air-gapped chart
gets the same change from a separate package.

**Input**, a nodepool entry in a cluster file (what step 5's template
writes):

```yaml
nodepool:
- infraEnvName: <infraenv>
  replicas: 3
  labels:
    allowDeletion: false
  annotations:
    redbull.io/scale-down-policy: fewest-pods
```

**Output**, its NodePool:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "4"
    redbull.io/scale-down-policy: fewest-pods
```

- A nodepool without `annotations` renders exactly as before, and so does
  every existing cluster file: render a few with and without the change
  and compare (the way [3.46-to-3.47.md](3.46-to-3.47.md) step 4 renders
  every file).
- The chart does not refuse an entry that sets
  `argocd.argoproj.io/sync-wave` itself; the NodePool would get the key
  twice. Wingman never writes it, and refuses an edit that adds it to an
  entry's `annotations`.

Anything else in the render: **STOP**.

## 5. The specs project's template (only to declare policies, through an MR)

Open an MR on the specs project that adds exactly these lines to
`cluster-template.j2`, directly below the `labels:` block of step 3.3.
Indent `annotations:` like `labels:` (four spaces in the reference) and the
key two more; the template tags start at column 0.

```jinja
{% if np.scale_down_policy | default("") %}
    annotations:
      redbull.io/scale-down-policy: {{ np.scale_down_policy }}
{% endif %}
```

- `| default("")` keeps the input optional: a nodepool without it renders
  as before, and so does the platform default (Wingman sends nothing).
- The value is one of `fewest-pods`, `least-requested`, `least-utilized`:
  day1 refuses any other before the template renders.
- Day1 checks that every rendered file holds exactly the policy chosen, and
  none where none was chosen. A flavor that gives one is refused while the
  template does not read it.

A person with rights on the specs project merges it. Record the MR. Do it
after step 4: a file with the annotation and a chart without the change
scale down at random, as before.

## 6. Upgrade

```bash
helm upgrade <release> $CHART -n <ns> --reset-then-reuse-values \
  --set image.day1.tag=<tag> --set image.day2.tag=<tag> --set image.web.tag=<tag>
kubectl -n <ns> rollout status deploy -l app.kubernetes.io/part-of=wingman --timeout=5m
```

## 7. Verify

1. Clusters and Flavors load as before.
2. Without step 5: `GET /api/day1/specs/template/schema` (with a session
   token, as in 3.3-to-3.4's step 8) does not list `scale_down_policy`
   under `nodepools`. With it: it does. On the create form, pick any flavor
   and an MCE, set the first nodepool's **Scale-down policy** to
   `fewest-pods`, and press **Preview** (it commits nothing). The file shows
   `annotations:` with `redbull.io/scale-down-policy: fewest-pods` under that
   nodepool only. Leave the form without creating.
3. With Scale on: on a cluster's Nodes tab, lower a NodePool's stepper by
   one and press **Scale down**. The confirmation offers **Which servers
   leave**, the NodePool's policy named. Press **Cancel**: nothing is sent.
   Don't scale a cluster to test it: a scale is a real commit to day1
   `main`.

## 8. Roll back and report

Roll back with `helm rollback <release> <previous revision> -n <ns>`. A file
that already has the annotation keeps it: 3.48 ignores it in every edit,
and update-nodepool still reads it. Revert step 5's MR only when no flavor
gives the input. A run started with a policy finishes as it began.

Report:
- the tag deployed;
- step 3's answers;
- the chart change and step 5's MR, if done;
- step 7's results.
